# UmbraWG userspace: архитектура Rust-реализации

Цель: заменить Go-реализацию (Go-версия сохранена в истории git) на Rust с сохранением
байтовой совместимости с модулем ядра `umbrawg` (протокол Noise IK + обфускация 3.1).

## Инварианты

1. Байты на проводе, номера netlink-атрибутов и UAPI-команды не меняются.
2. UAPI-совместимость: unix-сокет `/var/run/umbrawg/<iface>.sock`, команды `get=1` / `set=1`,
   формат ответов совместим с Go-версией.
3. Горячий путь без аллокаций: буферы из пула, батчинг, `recvmmsg`/`sendmmsg`.
4. Один поток на очередь (queue), без глобальных блокировок на пути пакета.
5. Поддержка Linux (TUN), сборка под x86_64 и aarch64/armv7.

## Крейты

| Крейт | Ответственность |
|---|---|
| `umbrawg-crypto` | blake2s, chacha20poly1305, x25519, tai64n, CSPRNG-обёртки |
| `umbrawg-proto` | константы и типы сообщений, заголовки, обфускация (H1-H4, S1-S4, Jc/Jmin/Jmax, I1-I5, padding, trailers), header protection |
| `umbrawg-noise` | состояние handshake (IK), вывод ключей, cookie/replay, TAI64N |
| `umbrawg-device` | Device/Peer, allowed-ips, timers, ratelimiter, очереди пакетов, state machine |
| `umbrawg-transport` | UDP-сокеты, GSO/GRO (`UDP_SEGMENT`/`UDP_GRO`), multi-queue, sticky sockets, fwmark |
| `umbrawg-tun` | TUN-устройство, multi-queue, virtio-net header, GSO/GRO offload |
| `umbrawg-uapi` | парсер/сериализатор UAPI, unix-socket сервер |
| `umbrawg` (bin) | демон: конфигурация, запуск очередей, обработка сигналов |

## Потоковая модель

```
TUN rx queue i ──> worker i ──> encrypt ──> UDP send (GSO, batch)
UDP socket j  ──> worker j ──> decrypt ──> TUN tx (GRO/offload)
```

- `n_workers = min(4, available_parallelism())`, конфигурируется `UMBRAWG_THREADS`;
  на хосте с ≤ 8 ГиБ RAM дефолт снижается до 2: там обычно живут десятки
  демонов, и каждый воркер стоит ~2 МиБ (приёмные буферы, скрэтч), TUN-очередь
  и UDP-сокет. В параллельном режиме это же значение используется, если не
  задан `UMBRAWG_RX_WORKERS`.
- Каждый worker владеет: TUN fd (очередь), UDP fd, буферным пулом, таймером (timerfd).
- Разделяемое состояние: `Arc<Device>`, пиры в `RwLock<PeerMap>`; горячий путь читает
  `Arc<Peer>` из lock-free снимка (`arc_swap`), обновление — под write-lock.
- Ключи и handshake-состояние пира — в `RwLock<Handshake>` с быстрым read-путём.
- Таймеры: один `timerfd` на worker + wheel; никаких потоков на пира.

### Бюджет памяти демона

Память демона — это фиксированная база плюс небольшие пулы на воркер:

| Статья | Размер | Решение |
|---|---|---|
| база (код, библиотеки, jemalloc-арены/rtree) | ~14 МиБ | не наша: аллокатор держит 2-МиБ extent'ы на потоки |
| приёмные буферы воркера | `RECV_BATCH × 64 КиБ` | `RECV_BATCH = 16` → 1 МиБ вместо 4 МиБ; буфер обязан вмещать GRO-суперпакет |
| скрэтч/батчи воркера | ~1 МиБ | `TUN_BATCH`, MTU |
| пул staged-пакетов | до 128 × 64 КиБ | ленивый: выделяется под фактическое окно рукопожатия |
| parallel: пул заданий + очередь управления | `depth × 64 КиБ × N`, 128 слотов | оба ленивые, в простое 0 |

Замеры (THP=always, jemalloc через `/etc/ld.so.preload`): 20 МиБ при одном
воркере, 24 при двух, 35 при четырёх; 51 демон под нагрузкой 50 пиров —
1.24 ГиБ при двух воркерах, 1.45 при трёх, 1.68 при четырёх.

`SO_RCVBUF`/`SO_SNDBUF` в бюджет не входят: это потолки, ядро выделяет
буферы по факту (`/proc/net/sockstat`: ≤ 6 МБ на всю нагрузку, 0 в простое).

На стенде 3.9 ГБ анонимная память ложится в ZONE_DMA32 (2 ГиБ), и ядро
включает OOM-киллер при её заполнении, выбирая самый крупный процесс (хаб).
Поэтому дефолт воркеров memory-aware: 2 на хосте ≤ 8 ГиБ RAM.

### Параллельный приём (`UMBRAWG_PARALLEL_RX=1`)
```
UDP socket ──> rx-поток: recvmmsg + detect + index lookup
                        │  выбор воркера: hash(public_key) % N (sched=peer)
                        │  ограниченные SPSC-очереди (64..1024 заданий, по умолчанию 64)
                        ├──> крипто-воркер 0 ──> open + replay + TUN queue 0 (GSO)
                        ├──> крипто-воркер N ──> open + replay + TUN queue N (GSO)
                        └──> очередь управления (128) ──> поток control:
                             handshake/cookie + under-load детектор
```

- По умолчанию выключен: однопоточный режим не меняется и не деградирует на 1 соединении.
- `UMBRAWG_RX_WORKERS` задаёт число крипто-воркеров; по умолчанию половина ядер, не
  больше четырёх (ядро остаётся RX-потоку, остальные — стеку, UAPI и прочей работе).
  Если `UMBRAWG_RX_WORKERS` не задан, пуст или нечисловой, берётся
  `UMBRAWG_THREADS` — общая ручка числа потоков демона, общая с классическим
  режимом (о подмене нечислового значения пишется `warn`). Всего потоков у
  процесса `N + 2`: N крипто-воркеров, поток приёма и поток управления.
- Память и масштаб: для 50 пиров на стенде с 4 ГБ RAM используется
  `UMBRAWG_RX_WORKERS=2` и `UMBRAWG_RX_QUEUE=64` (дефолт). Пулов на процесс
  тогда 8 МиБ (верхняя граница), потоков — 4 + UAPI. При старте демон пишет
  верхнюю границу пула и предупреждает, если она больше четверти
  `MemAvailable`; рекомендация — держать общий бюджет 51 демона ниже объёма
  RAM, иначе OOM-киллер убьёт случайный процесс (чаще всего хаб, у которого
  больше всего состояния).
- `UMBRAWG_RX_SCHED=peer` (по умолчанию) привязывает пира к воркеру по
  `hash(public_key) % N` (FNV-1a): все транспортные сегменты пира идут в один воркер,
  порядок внутри пира сохраняется, разные пиры распределяются по воркерам. Состояние
  сессии пира (replay-фильтр, таймеры) трогает только его воркер.
- `UMBRAWG_RX_QUEUE` задаёт глубину очереди заданий и пула буферов воркера:
  степень двойки от 64 до 1024, по умолчанию 64 (4 МиБ); верхняя граница памяти на
  воркера — `глубина × 64 КиБ`, некорректное значение — ошибка при старте. Буферы
  слотов выделяются лениво, по длине фактической дейтаграммы, поэтому простаивающий
  пул не занимает память, а глубина ограничивает только всплеск под нагрузкой.
- `UMBRAWG_RX_SCHED=queue` — эксперимент: задание уходит в наименее загруженную очередь.
  Суммарная скорость выше, но пакеты одного потока переставляются и TCP ретранслирует.
- Дейтаграмма (включая GRO-суперпакет) целиком уходит одному воркеру: воркер определяет
  первый транспортный сегмент, остальные сегменты (в том числе разные пиры в одной
  дейтаграмме — аномалия, счётчик `mixed_peers`) идут в то же задание без потерь.
  Порядок сегментов внутри дейтаграммы сохраняется, GSO-склейка в TUN работает.
- Управляющие пакеты (рукопожатие, cookie) классифицируются потоком приёма, копируются
  в ограниченную очередь (128 пакетов) и обрабатываются отдельным потоком
  `umbrawg-control`. Поток приёма не выполняет X25519 и не ждёт локов рукопожатия,
  поэтому флуд инициаций не останавливает данные. Переполнение очереди управления —
  дроп со счётчиком `control_drops`; ёмкости хватает на всплеск, а лишнее отбрасывается
  без влияния на очереди крипто-воркеров.
- Replay-фильтр ключа — `AtomicReplayFilter` (массив `AtomicU64` c `fetch_or`): проверка
  повтора не сериализует воркеров. Переполнение очереди выбранного воркера — дроп с
  счётчиком `drops(queue)` (`UMBRAWG_RX_STATS=1`); на другой воркер задание не
  перекидывается, иначе порядок пира сломался бы. Память ограничена сверху: глубина
  очереди (`UMBRAWG_RX_QUEUE`, по умолчанию 64 задания) × 64 КиБ = 4 МиБ на воркера
  (16 МиБ процесс при 4 воркерах); слоты выделяются под длину фактического пакета,
  поэтому в простое пул пуст. Верхняя граница пула входит в стартовый лог и в
  предупреждение о бюджете памяти. Управляющие пакеты идут не в пул, а в очередь
  управления (128 слотов, каждый — по длине пакета): при флуде сверх лимита новые
  пакеты отбрасываются со счётчиком `control_drops`, данные при этом продолжают
  идти. Счётчик `enqueued` в статистике считает только задания воркерам,
  управляющие дейтаграммы в него не входят.
- Отдельный случай: дейтаграмма без единого транспортного сегмента (только
  рукопожатие/cookie) не публикует задание воркеру — она уже лежит в очереди
  управления, а слот пула и пробуждение воркера на пустую расшифровку не нужны.
- Завершение: поток приёма прекращает `recvmmsg` и снимает сокет; воркеры
  дочитывают очередь и возвращают слоты в пул, поток управления — очередь
  управления — одним проходом, поэтому `join` укладывается в ~200 мс и
  SIGTERM не требует `kill -9`.

### Защита от флуда инициаций

Детектор `under_load` живёт в `umbrawg-device` (`underload.rs`) и не меняет формат
провода:

- считает инициации, прошедшие MAC1, в скользящем окне 1 с (10 корзин по 100 мс);
- порог `UMBRAWG_UNDER_LOAD_PPS` (по умолчанию 100/с), вход при `total >= порога`,
  выход при `total * 2 <= порога` (гистерезис);
- состояние обновляется при каждой инициации и периодически в housekeeping /
  потоке управления, поэтому после прекращения флуда флаг снимается без трафика;
- при установленном флаге инициация до X25519 требует валидный MAC2, иначе уходит
  cookie-ответ; после MAC2 срабатывает существующий rate limiter (20/с на адрес,
  IPv6 — `/64`);
- `UMBRAWG_UNDER_LOAD=0` отключает детектор (для замеров), по умолчанию защита
  включена; `DisableCookies` в параметрах обфускации оставляет только очередь и
  внешний rate limit.

Замер: `scripts/test-control-flood.sh` — два netns, поток 5000 инициаций/с,
TCP через туннель. Проверяются `under_load=1`, отсутствие дропов данных и
снижение пропускной способности не более чем до 50 % от базовой.

## Горячий путь (требования)

- Буферы 64 KiB, выравнивание под virtio-net header; пул на worker.
- `recvmmsg` до 64 датаграмм за вызов, `sendmmsg` с `UDP_SEGMENT` (GSO) до 64 сегментов.
- `UDP_GRO` на приёме, склейка в `virtio_net_hdr` для TUN.
- ChaCha20-Poly1305: одна инициализация состояния на пакет, без промежуточных `Vec`.
- Обфускация: заголовки H1-H4 и junk-префиксы S1-S4 формируются в тот же буфер без копий;
  I1-I5 и trailers — из предвычисленных шаблонов (аллокация только в control path).
- Паддинг данных выбирается **один раз на батч отправки**, а не на пакет: иначе у
  каждого сегмента своя длина и GSO-склейка разваливается (см. «GSO и рандомный
  паддинг»).
- Никаких `format!`, `log` по уровню выше `debug` в горячем пути; счётчики — атомарные.

## Обфускация 3.1

Параметры (`H1..H4`, `S1..S4`, `Jc/Jmin/Jmax`, `I1..I5`, `HeaderProtectionKey`,
`ContentPaddingAddition`, `RandomTrailers`, `DisableCookies`) задаются через UAPI/INI
и применяются идентично модулю ядра.

Семантика (эталон — `umbrawg-linux-kernel-module/src/{peer.c,junk.c,header_protection.c,send.c,receive.c}`
и Go-реализация в истории git):

- каждый тип сообщения (1..4) получает случайный заголовок из соответствующего диапазона Hx;
- перед заголовком добавляется `Sx` случайных байт;
- junk-пакеты (Jc штук размера Jmin..Jmax) отправляются перед handshake;
- I1-I5 — специальные пакеты с тегами `<b>`, `<rc>`, `<r>`, `<t>`, `<rd>`;
- padding контента: `ContentPaddingAddition` — случайная добавка к выравниванию;
- trailers: случайный хвост после шифротекста, отбрасывается при приёме;
- header protection: ChaCha20 по части заголовка с ключом из конфигурации.

### GSO и рандомный паддинг

Инвариант: **пакеты с одинаковым plaintext в одном батче отправки обязаны иметь
одинаковую длину на проводе**. `UDP_SEGMENT` склеивает только сегменты одного
размера (кроме последнего), а `BatchLayout` в `umbrawg-device` группирует
датаграммы именно по `segment_len`. Поэтому `ContentPaddingAddition` и
`RandomTrailers` разыгрываются один раз на батч (`Device::pick_batch_padding`)
и применяются ко всем пакетам этого батча:

- батч — это один TSO-агрегат из TUN, то есть обычно 20–44 пакета; внутри
  батча длины равны, и GSO отправляет серию одинаковых сегментов одной
  супер-датаграммой (`send_split`). Это максимум случайности, который GSO
  допускает: на проводе сегменты супер-датаграммы всё равно равны;
- между батчами добавка случайна, распределение (`51..197`, `0..window` или
  резерв `0..15`) сохраняется, и по одной датаграмме размеры не выводятся;
- `ContentPaddingAddition` ограничена свободным местом в окне пира, поэтому
  полный пакет может получить **0 добавки** — ровно как
  `uwg_peer_skb_randomize_padding_addition` в модуле ядра. Резерв
  `RandomTrailers` `0..=15` при этом сохраняется всегда: окном он не режется
  (в ядре это `UWG_TRAILER_RANDOM_MIN`), иначе полные пакеты уходили бы
  детерминированной длины;
- одиночные пакеты (`send_data`/`send_packet`, `encrypt_packet`) по-прежнему
  получают собственное случайное значение — им склеивать нечего.

Окно `udp_window` пира на отправке пополняется **непадированной** длиной
(`s4 + 16 + plaintext + 16`), а на приёме — полной длиной датаграммы вместе с
AEAD-тегом (`header_end + plaintext + 16`), как в модуле ядра: иначе
собственная добавка раздувает окно, а окно — следующую добавку, и одиночные
ACK уезжают размером с полный MTU.

### Порядок классификации

`MessageKind::DETECTION_ORDER` проверяет transport первым. При
`RandomTrailers` проверка длины для всех типов ослаблена до `>=`, поэтому
каждый пакет данных иначе сверяется ещё и с H1..H3 по чужому смещению. Ширина
диапазонов профиля (~69 тыс. значений из 2^32) даёт ~4 ложных срабатывания в
секунду под полной нагрузкой, а каждое — молчаливый дроп и сброс TCP-окна.
Настоящий transport-пакет всегда декодируется в H4 по своему смещению, так
что проверка его первой убирает ложные срабатывания из горячего пути; у
handshake остаётся ~4e-6 шанса случайно совпасть с H4, его закрывает retry.

## Совместимость

- Паритетные тест-векторы handshake и обфускации против Go-реализации (в истории git).
- Interop-матрица: Rust↔kernel, kernel↔Rust, Rust↔Rust, kernel↔kernel,
  с обфускацией и без, 1/4/5 пиров.
- `uwg` (Rust CLI в отдельном репозитории `umbrawg-tools`) конфигурирует и демон, и модуль.
- UAPI-ключ пира `advanced_security` принимается в `set=1` и отражается в
  `get=1` (только если был задан). Userspace-демон хранит его как
  информационное поле и не реализует advanced security; реальная защита
  доступна только в модуле ядра (`UWGPEER_A_ADVANCED_SECURITY`).
- Per-peer шифр transport-пакетов (`UWGPEER_A_CIPHER`): по умолчанию
  ChaCha20-Poly1305, опционально AES-256-GCM. Handshake, cookie, обфускация и
  размеры сообщений не меняются; ключ сессии используется напрямую в обоих
  AEAD, поэтому Rust, ядро и совместимые реализации расшифровывают пакеты друг
  друга при одинаковом значении `Cipher` на обеих сторонах. AES-256-GCM
  использует `ring` (features `aes-ring` и `ring-chacha`, по умолчанию в
  демоне) с fallback на RustCrypto; ChaCha и AES на стенде обгоняют `go`.

## Быстрый путь (fast path)

Архитектура быстрого пути не меняет байты на проводе и UAPI (инвариант 1):
все оптимизации локальны для демона и прозрачны для пиров.

- TUN offload + батч-чтение: `TUN_BATCH = 128` сегментов за один `read_batch`;
  запись в TUN — батчами с GSO-склейкой (до 64 сегментов на суперпакет).
- Отправка: `sendmmsg` с `UDP_SEGMENT` (UDP GSO), склейка одинаковых датаграмм
  к одному пиру в один вызов.
- Приём: `recvmmsg` + `UDP_GRO`; GRO-батч записывается в TUN одним
  GSO-суперпакетом с флагом `VIRTIO_NET_HDR_F_NEEDS_CSUM`
  (`VIRTIO_NET_HDR_GSO_UDP_L4`/TCP).
- Параллельный приём (`UMBRAWG_PARALLEL_RX=1`): RX-поток `recvmmsg` +
  классификация + поиск сессии, SPSC-очереди заданий и `N` крипто-воркеров
  с `AtomicReplayFilter`; дейтаграмма целиком уходит одному воркеру, воркер
  выбирается по пиру (`UMBRAWG_RX_SCHED=peer`).
- Память ограничена: 64 задания × 64 КиБ (4 МиБ) на воркера под нагрузкой, буферы
  слотов выделяются лениво; переполнение очереди выбранного воркера — дроп со
  счётчиком, без миграции на другой воркер.

Инварианты быстрого пути:

- байты на проводе, номера netlink-атрибутов и UAPI-команды не меняются;
- порядок байт внутри одной дейтаграммы (включая GRO-суперпакет) сохраняется;
- порядок пакетов внутри пира сохраняется и в параллельном приёме (`sched=peer`);
- UAPI `advanced_security` и прочие ключи обрабатываются идентично
  однопоточному режиму; userspace-демон не реализует advanced security.
- Peer-affinity (`sched=peer`) сохраняет порядок пакетов внутри пира, но общий
  выигрыш по throughput не подтверждён (final3: rust-par медленнее rust на 1–16.6%
  на одном пире); см. [tools/docs/RESULTS.md](tools/docs/RESULTS.md).

## Производительность

- Baseline: Go-реализация и оригинальный Go-демон.
- Цель: +30% на 1 ядре, +60% на 4 ядрах (TCP и UDP), без регресса обфускации.
- Профилирование: `perf record` + flamegraph, `strace -c`, счётчики softirq; правки только по профилю.
- Fast-path (TUN offload, GSO/GRO, `sendmmsg`/`recvmmsg`) дал +12.6…+103% относительно
  исходной userspace-реализации; финальные замеры (final3) — в
  [tools/docs/RESULTS.md](tools/docs/RESULTS.md) и разделе «Производительность» README.
- Параллельный приём с привязкой по пиру (`UMBRAWG_RX_SCHED=peer`) сохраняет порядок
  пакетов внутри пира, но общий выигрыш по throughput не подтверждён: rust-par медленнее
  обычного rust на 1–16.6% на одном пире во всех 8 ячейках final3; цели +30%/+60% не
  достигнуты. Режим остаётся opt-in/экспериментальным; default-on не рекомендуется.
  Ядро (`kernel-umbrawg`) достигло цели +30% на c=1 относительно `kernel-amneziawg`.
