# BBRv3 и FEC: состояние интеграции

Ветка: `feature/bbrv3-fec`. Master и релиз `v0.1.0` не затронуты:
по умолчанию `bbr=off`, `fec=off`, накладных расходов нет.

## FEC

- Reed-Solomon GF(256), блоки `k+m`, восстановление любых `m` стираний.
- Режимы: `off`, `fixed K:M`, `adaptive`.
- `adaptive`: FEC выключен на чистом канале; включается при loss > 1%
  (окно 256 пакетов, после 1024 пакетов прогрева) и выключается после
  5 секунд с loss < 0.2%.
- TUN GSO остаётся включённым. Внешние GSO-группы при активном FEC
  ограничены `m` шардами, чтобы потеря GSO-агрегата не убивала больше
  `m` шардов; ограничение применяется к живым сокетам динамически.
- FEC работает над внешними IP-пакетами и не различает TCP/UDP/ICMP.

### Замеры (veth 9000, 3c, один поток)

| Сценарий | Скорость | Потери/результат |
|---|---:|---|
| TCP clean, FEC off | 3267–3493 Мбит/с | — |
| TCP clean, FEC adaptive (не активен) | **3330 Мбит/с** | без регрессии |
| UDP 200M loss 2%, FEC off | 196.1 Мбит/с | 1.967% |
| UDP 200M loss 2%, FEC fixed 10:2 | 199.7 Мбит/с | **0.036%** |
| UDP 200M loss 2%, FEC adaptive 2:1 | 198.9 Мбит/с | **0.316%** |
| TCP loss 2%, FEC fixed 2:1 | **457 Мбит/с** | лучше TCP без FEC (213) |
| TCP loss 2%, FEC adaptive 2:1 | **440 Мбит/с** | лучше TCP без FEC |
| TCP clean, FEC fixed 10:2 | 1870 Мбит/с | цена fixed-режима |
| TCP loss 2%, FEC fixed 10:2 | 30 Мбит/с | большой блок не успевает |

## BBRv3

- ACK-based state machine (BtlBw/RTprop, Startup/ProbeBw/ProbeRtt,
  inflight_hi/lo) интегрирован; DRAIN для туннеля пропускается, потому
  что очередь приложения находится снаружи.
- Пейсер работает на батчах; TUN-пакеты накапливаются между чтениями,
  мелкие батчи не спят.
- BBR имеет bounded per-peer очередь (1024 пакета / 4 МиБ), чтобы не
  блокировать воркер на ожидании ACK.
- Пейсер применяется к многопакетным батчам, не к каждому пакету;
  мелкие батчи не спят, долг копится в token bucket.
- UDP 200M на линке 100M: off 92.1 Мбит/с / 52.1% потерь, on
  91.8 Мбит/с / **43.0%** — скорость не падает, потери ниже.
- Малые пакеты (≤256 Б, включая ICMP/ACK) обходят BBR-очередь.
- RTT под нагрузкой: off ~76 мс, on ~82 мс (max 104) — близко.
- TCP clean: on 3840 Мбит/с, off 3267–3493 — регрессии нет.
- `bbr=on` пока экспериментальный; жёсткий cwnd-лимит не включён,
  используется pacing + bounded queue.

## Ограничения

- Fixed FEC для TCP на малом RTT может ухудшать throughput: блок
  собирается дольше, чем TCP успевает войти в recovery. Для TCP
  использовать adaptive (на чистом канале не активен), либо ждать
  уменьшения `k`/задержки блока.
- GSO-группа при FEC ограничена `m`; это снижает syscall-батчинг, но
  сохраняет восстановление.
- Конфиг/CLI/UAPI: `BBR`, `FEC`, `uwg set bbr/fec`, ключи `bbr=`/`fec=`
  работают для userspace-демона. Env `UMBRAWG_BBR`, `UMBRAWG_FEC`,
  `UMBRAWG_FEC_SHARD`, `UMBRAWG_ACK_INTERVAL` остаются для стенда.
- Netlink: `UWGDEVICE_A_BBR=36` (u8 0/1/2) и `UWGDEVICE_A_FEC=37`
  (`0`/`1`/`(K<<8)|M`) уже принимаются и отдаются модулем и tools.
- Ядро: `ext.c`/`ext.h`, приём CAPS/ACK/FEC_SHARD и отправка CAPS/ACK
  через crypto-queue. CAPS: до 3 попыток (первые — через 250 мс, затем
  раз в 2 с) и переотправка при получении чужих CAPS/любом трафике;
  ACK: каждые 2 пакета/1 мс, bitmap 64 бита, ACK-на-ACK исключён.
- Модуль анонсирует ACK и FEC (BBR в CAPS не анонсируется). FEC data-plane
  в ядре работает как kernel↔kernel, так и с Rust-демоном.
- Добавлен kernel FEC-кодек `fec.c/h`: GF(256) 0x11d, систематический
  RS до 32+16, encode/decode без kmalloc, матрица 1:1 с Rust
  (проверено сравнением), selftest при загрузке модуля.
- Добавлен kernel BBR-контроллер `bbr.c/h`: BtlBw/RTprop,
  Startup/ProbeBw/ProbeRtt, pacing/cwnd/inflight, ring 2048×24 Б
  (~48 КиБ), selftest в `uwg_mod_init` (99.9% полосы на синтетике).
- BBR-пейсинг включён в kernel data-plane: per-peer `uwg_bbr` под RCU,
  `on_send` на transport-пакетах, `on_ack` в обработчике ACK, задержка
  token bucket в tx workqueue (только bbr=on, пакеты ≥512 Б, вне
  atomic/softirq). На tbf 100 Мбит: 89.5 против 92.5 Мбит/с без BBR —
  регрессии нет. BBR в CAPS не анонсируется.
- FEC data-plane в ядре реализован для fixed/adaptive профилей k≤8,m≤2:
  TX собирает блоки (partial по таймеру 1 мс), RX восстанавливает и
  отдаёт в TUN с порядком/таймаутом 5 мс. Лимит FEC-TX — `mtu + 2`
  (учтён префикс длины шарда), поэтому полноразмерные TCP-сегменты
  попадают в FEC, а не уходят legacy.
- `adaptive` в ядре настоящий: оценка потерь по входящим transport-
  счётчикам, включение при >1% после прогрева 1024 пакетов,
  выключение через 5 с при <0.2%. Как и в Rust, оценка предполагает
  симметричные потери; при односторонних потерях сторона с чистым
  входящим потоком останется в legacy.
- Смешанный kernel↔Rust FEC работает, включая bulk. Найдены и
  исправлены три причины: Rust не отвечал CAPS, если уже получил
  чужие; ядро копировало пакет в шард до финализации контрольной
  суммы (Rust-TUN дропал TCP/UDP); первый CAPS мог потеряться в гонке
  с установкой ключей, и сторона замолкала.
- При смене BBR/FEC через netlink CAPS переотправляется
  (`uwg_ext_caps_changed`).
- Профили k>8/m>2 (например 10:2) в ядре пока идут legacy.
- Замеры после фиксов (veth, underlay MTU 9000, TUN MTU 1420, netem
  loss 2% на egress ядра, iperf3 4 с):

| Сценарий | TCP | UDP 400M |
|---|---|---|
| mixed kernel↔Rust, FEC off | 257 Мбит/с | 2.1% |
| mixed kernel↔Rust, fixed 2:1 | **452 Мбит/с** | **0.3%** |
| kernel↔kernel, fixed 2:1 | **663 Мбит/с** | **0.2%** |
| mixed, adaptive, чистый канал | 2635 Мбит/с | 0.0% |
| mixed, fixed 2:1, чистый канал | 1460 Мбит/с | 0.0% |

- BBR + FEC вместе (после фикса пейсера, см. ниже):

| Сценарий | TCP | UDP 400M |
|---|---|---|
| mixed, bbr on + fixed 2:1, чистый | 1580 Мбит/с | 0.0% |
| mixed, bbr on + fixed 2:1, loss 2% | **474 Мбит/с** | **0.1%** |
| kernel↔kernel, bbr on + fixed 2:1, чистый | 1032 Мбит/с | 0.0% |
| kernel↔kernel, bbr on + fixed 2:1, loss 2% | **707 Мбит/с** | **0.1%** |

- BBR-пейсер не применяется к FEC-шардам: шарды — это расширение
  исходного потока (k+m на k пакетов), и пейсинг каждого шарда
  применял token bucket к расширению, роняя rate в сотни раз
  (kernel↔kernel: 3 Мбит/с против 1000+). Pacing по-прежнему учитывает
  исходную отправку в `uwg_bbr_on_send()`; при включённом FEC пейсинг
  фактически не ограничивает FEC-трафик.
- Пейсинг на уровне блока (первый шард несёт длину всего блока) был
  реализован и проверен: mixed работает (1580/474), но kernel↔kernel
  снова схлопывается до ~7 Мбит/с. Причина глубже пейсера: сэмплер
  delivery rate в `bbr.c` берёт время постановки пакета в ring, а не
  фактической отправки, поэтому задержка пейсинга занижает оценку
  (интервал 20 мс на 1400 байт → 70 КБ/с), и BBR выходит из Startup
  с низким BtlBw. Часть пакетов при этом вообще не находит свой слот
  в ring (`match=0`). Это отдельная задача по BBR; до её решения
  пейсинг FEC-трафика отключён.

## Следующие шаги

1. Батчевый BBR-пейсер (token bucket на батч, cwnd/inflight).
2. Адаптивный FEC для TCP: меньший `k`, block deadline < RTT.
3. Конфиг/CLI/netlink, затем порт в ядро.
4. Матрица против amneziawg-go на loss/rate.
