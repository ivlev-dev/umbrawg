# BBRv3 и FEC: состояние интеграции

Релиз 0.4.0 (2026-11-20). По умолчанию `bbr=off`, `fec=off`: CAPS, ACK и
FEC-заголовки не добавляются, накладных расходов нет.

0.4.0 закрывает остатки аудита: безопасность обфускации, экспорт метрик,
epoch/keypair в BBR-ринге, MTU-политику FEC и применение `cwnd`.

Документ фиксирует состояние после волн 1–3 и финальные замеры. Формат
расширения описан в [`PROTOCOL-EXT.md`](PROTOCOL-EXT.md).

## Что работает

- FEC: Reed-Solomon GF(256), fixed-профили и adaptive `2:1`.
- BBRv3: token-bucket пейсер + Startup/ProbeBW/ProbeRTT, loss-сигнал из
  ACK, ring 4096, GSO для FEC-шардов.
- Обратная связь: CAPS с ограниченным числом попыток, ACK с bitmap 64 бита
  и случайной каденцией.
- Ядро и Rust-демон совместимы по wire-format и по профилям `k<=8, m<=2`.
- Обфускация control/FEC-трафика: случайные хвосты, порядок шардов, джиттер
  блока, случайный DSCP handshake.

## FEC

- Кодек: систематический RS над GF(256), полином `0x11d`, до `32+16`
  шардов в библиотеке ядра; data-plane ядра принимает `k<=8`, `m<=2`.
- Режимы: `off`, `fixed K:M`, `adaptive`.
- Adaptive — это включение профиля `2:1`, а не динамический `m`:
  - окно оценки — не менее 256 ожидаемых outer-counter'ов;
  - EWMA `(old * 3 + new) / 4` в 1/65536;
  - включение после прогрева 1024 counter'ов при loss `> 1%`;
  - выключение после 5 секунд при loss `< 0.2%`;
  - пороги, окно и прогрев одинаковы в ядре и Rust.
- FEC-TX включается только при совпадении `k:m` из CAPS. При разных
  профилях пакеты идут legacy, а не теряются молча.
- TUN GSO остаётся включённым. FEC-шарды одного блока имеют одинаковую
  длину и агрегируются в GSO-группы; случайный порядок шардов этому не
  мешает.
- RX хранит до 16 блоков, восстанавливает при `k` из `k+m`, отдаёт в
  порядке `block_id/index`; таймаут блока 5 мс (квантуется HZ).
- Partial-блок по таймеру `0.5..2 мс` уходит без parity (`m=0`).
- FEC не различает TCP/UDP/ICMP: защищаются любые внутренние IP-пакеты,
  которые помещаются в бюджет шарда.

### Бюджет MTU и политика underlay

Устройство хранит `underlay-mtu` (по умолчанию 1500). При включённом FEC
MTU интерфейса уменьшается до `underlay_mtu − 48 (IPv6+UDP) −
wire_overhead`, где `wire_overhead` включает transport-заголовок и тег,
ext/FEC-заголовки, двухбайтную длину, выравнивание и случайный хвост.
При выключении FEC MTU восстанавливается; ручной `ip link set mtu`
принимается как новая база при следующем `SET_DEVICE`.

- Ядро: `UWGDEVICE_A_UNDERLAY_MTU` (40), лимит шарда считается от
  уменьшенного MTU, поэтому полноразмерный для этого MTU TCP-пакет
  защищается FEC, а не уходит legacy.
- Rust: `UMBRAWG_UNDERLAY_MTU`; лимит шарда и MTU TUN выводятся из него,
  датаграмма шарда укладывается в бюджет (1500 → MTU 1352, шард 1385).
- При underlay 9000 MTU не уменьшается (1420), лимит шарда упирается в
  потолок 1900.
- При underlay меньше ~700 байт MTU упирается в 576; пакеты выше бюджета
  шарда остаются legacy.
- `S4` не входит в бюджет шарда, как и в legacy-пути; большие значения
  могут вывести датаграмму за underlay MTU.

## BBRv3

- ACK-based контроллер: BtlBw/RTprop, Startup/ProbeBw/ProbeRtt,
  `inflight_hi/lo`.
- DRAIN в ядре пропускается: после Startup сразу ProbeBW с gain 1.0.
- Пейсер — token bucket в tx workqueue; пакеты `< 512` байт не задерживаются.
- FEC-блок пейсится как целое: первый шард несёт `pace_len`, остальные
  уходят сразу. Bucket применяется к исходному потоку, а не к `k+m`.
- Ring 4096 × 24 Б (96 КиБ на пира). Loss-сигнал — дыры bitmap и
  watermark; реальные потери режут `inflight_hi/lo`.
- `cwnd` применяется как ACK-clocked гейт после loss-cut: только при
  `full_bw_reached && inflight_hi < cwnd`. Effective-окно —
  `max(cwnd, pacing_rate × 5 мс)` с потолком 4 MiB, плюс аварийный выход
  через 5 мс без ACK. На чистом канале и в STARTUP ограничивает только
  пейсер, поэтому sleep-потолок не возвращается.
- BBR-ринг привязан к keypair: смена keypair очищает ring, ACK чужого
  keypair игнорируется.
- Метрики BBR/FEC отдаются в `uwg show <if> bbr-stats|fec-stats`.
- `SO_TXTIME`/ETF и kernel EDT/fq не используются: задержка считается
  программно, сон/батч в tx workqueue.
- Header protection читается под RCU; матрица RS кэшируется по `(k,m)`;
  FEC-шарды идут через GSO.
- BBR не анонсируется модулем ядра в CAPS: CAPS нужен только для ACK/FEC.
  `bbr=on` включается вручную на обеих сторонах.
- Rust BBR проверяет наличие `ACK` в CAPS пира; ядро такой проверки не
  делает (см. «Ограничения»).
- Порог loss-реакции: ядро 20% раунда, Rust 2%. Это разные эвристики,
  а не общий параметр.

## Обратная связь и обфускация

- CAPS: до 3 автоматических попыток; повторы через ~250 мс, после третьей
  пауза 2 с. Переотправка — при изменившемся CAPS пира (одна) и при смене
  `bbr`/`fec` через netlink/UAPI. Идентичные CAPS не отвечают, пинг-понга
  нет.
- ACK: bitmap 64 бита; отправка каждые `8..16` принятых data/FEC-пакетов
  или через `2..5 мс`, значения случайны на каждый цикл. На простое ACK не
  шлётся. ACK-на-ACK исключён: CAPS/ACK обновляют bitmap, но не запускают
  новый ACK.
- Восстановленные FEC-пакеты **не** помечаются в ACK: в шарде нет внешнего
  counter потерянного пакета. Для отправителя дыра остаётся, и BBR может
  учесть её как потерю. Это ограничение, а не «FEC скрывает потери от BBR».
- Обфускация: data-padding по конфигу, control-кадры `0..15`,
  `shard_len + 0..31`, случайный порядок шардов, джиттер блока
  `0.5..2 мс`, случайный DSCP handshake в модуле ядра,
  random trailers с запасом до MTU.
- `bench/detect.py` — офлайн-анализ pcap: гистограмма размеров, `len % 16`,
  ACK-часы, серии одинаковых размеров, автокорреляция, IP-фрагменты.

## Финальные замеры

Стенд: veth, underlay MTU 9000 (если не указано иное), TUN MTU 1420,
iperf3; «mixed» — kernel↔Rust, «kk» — kernel↔kernel.

### FEC 2:1

| Сценарий | Результат |
|---|---|
| clean, mixed | **2.8 Гбит/с** |
| clean, kk | **2.6–2.7 Гбит/с** |
| 2% потерь в обе стороны, UDP 400M | **0.1–0.3% потерь** |
| 2% потерь в обе стороны, TCP | **90–290 Мбит/с** (полноразмерные сегменты идут legacy) |
| underlay 1500, UDP | **0.1% потерь, IP-фрагментов 0** |

### BBR + FEC 2:1

| Сценарий | Результат |
|---|---|
| clean | **2.7–2.8 Гбит/с** |
| 2% потерь, UDP 400M | **0.1–0.3% потерь** |

### Простой и детектируемость

| Проверка | Результат |
|---|---|
| 10 секунд без трафика | **4 пакета** (CAPS/keepalive, без ACK-метронома) |
| `bench/detect.py` на реальном дампе | **OK: 10 PASS, 1 SKIP** |
| top-1 доля размера | **5.1%** |
| энтропия `len % 16` | **3.86 бит** |
| доля ACK-часов | **4.3%** |
| max_run одинаковых размеров | **6** |

## Ограничения

- `cwnd` ограничивает отправку только после loss-cut и выхода из STARTUP.
  На чистом канале окно намеренно не подменяет пейсер: ACK-каденция
  8–16 пакетов иначе задаёт потолок на малом RTT.
- MTU при включённом FEC уменьшается (1500 → 1352 в Rust, 1368 в ядре);
  это снижает MSS. Для 9k-подложки укажите `underlay-mtu 9000`, чтобы
  сохранить MTU 1420.
- Потолок шарда Rust 1900 байт: при underlay больше ~2015 байт полный
  пакет 1420 защищается, иначе лимит ниже и часть крупных пакетов идёт
  без FEC.
- Adaptive оценивает потери по входящему потоку и предполагает симметрию.
  При односторонних потерях сторона с чистым входящим потоком останется в
  legacy.
- Восстановленные FEC-пакеты не отмечаются в ACK; BBR может считать их
  потерями. FEC защищает приложение, но не скрывает потери от контроллера.
- BBR по умолчанию выключен. Ядро не анонсирует BBR в CAPS и не проверяет
  `ACK` пира перед пейсингом: при `bbr=on` и пире без extension фидбека не
  будет. Включайте BBR только с обеих сторон.
- Fixed FEC на малом RTT может ухудшать TCP: блок собирается дольше, чем
  TCP входит в recovery. Для TCP предпочтителен adaptive.
- FEC `k+m` даёт overhead `(k+m)/k`; на 2:1 это +50% пакетов. На узком
  месте выигрыш FEC может быть меньше цены расширения.
- Порог loss-реакции BBR в ядре (20%) и Rust (2%) различается.
- Таймеры `2..5 мс` и `5 мс` квантуются HZ; при `HZ=250` шаг 4 мс.
- Rust-потолок шарда 1900 байт не пересчитывается из underlay MTU.

| UAF таймеров FEC в ядре | Закрыт: `timer_shutdown_sync`, флаг `disabled`, порядок с `synchronize_net` |

| Валидация ACK | Закрыт: `largest <= max_sent`, ограничение `ack_delay` |
| MTU-бюджет FEC | Закрыт: бюджет от `underlay-mtu`, MTU понижается при FEC и восстанавливается |
| Невыровненные обращения в приёме | Закрыт: `get_unaligned_*` |
| Секреты в bench-конфигах | Закрыт: плейсхолдеры вместо ключей |
| Netlink принимает неподдерживаемые `k:m` | Закрыт: `-EINVAL` вне `k<=8, m<=2` |
| BBR без подтверждения ACK | Частично: Rust проверяет `ACK` в CAPS; ядро пейсит при `bbr=on` без проверки, но BBR не анонсируется и требует ручного включения |
| Loss-сигнал BBR не использовался | Закрыт: дыры bitmap/watermark вызывают loss cut после Startup |
| Ring 2048 не покрывал BDP | Закрыт: ring 4096 |
| GSO не обновлял `on_sent`, утечки `inflight` | Закрыт: `on_sent` на GSO-группу, `on_drop` на drop-путях |
| ACK-часы и фиксированный padding | Закрыт: случайная каденция, control/FEC-хвосты, `shard_len + 0..31` |
| FEC-лимиты Rust расходились с ядром | Частично: decoder/encoder ограничены, бюджет шарда выводится из underlay; Rust по-прежнему допускает `k+m<=255` в библиотеке, ядро — `k<=8, m<=2` |

## Следующие шаги

1. Отмечать восстановленные FEC-пакеты в ACK, если появится внешний
   counter в шарде (wire-version 2).
2. Свести loss-порог BBR ядра и Rust к одному значению.
3. Проверить автоматический откат BBR при пире без ACK в ядре.
4. Поднять потолок шарда/floor cwnd при переходе на сети >6 Гбит/с.
5. Матрица против `amneziawg-go` на loss/rate.
