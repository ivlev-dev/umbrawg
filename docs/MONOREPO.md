## Правила

1. **Один PR — один компонент или одна сквозная задача.** Сквозные изменения
   (UAPI в модуле + netlink-крейт + `uwg`) делаются одним PR: в этом смысл
   монорепо.
2. **Три независимых Cargo workspace.** Не объединять `umbrawg-tools`,
   `umbrawg-rs` и `netlink-packet-umbrawg` в один workspace: разные MSRV
   (1.85/1.88), лицензии (GPL-2.0-only/MIT) и профили (`panic = "abort"`).
3. **Теги с префиксом компонента** (`kernel-v*`, `netlink-v*`, `tools-v*`,
   `rs-v*`). CI и упаковка реагируют только на свой префикс.
4. **CI по путям.** Изменения в `docs/` и `bench/` не должны пересобирать
   модуль ядра и крейты.
5. **Результаты замеров не коммитим.** В `bench/` живут только скрипты,
   конфиги и небольшие эталонные CSV; сырые результаты — на стенде.
6. **Секреты не коммитим.** `bench/keys.env` в `.gitignore`, в репозитории
   только `bench/keys.env.example`.

## Как выпустить релиз

1. Обновить версию в манифесте компонента (`src/version.h`, `Cargo.toml`,
   `debian/changelog`, spec — что применимо).
2. Прогнать упаковку вручную (без публикации, релиз пропускается):
   `gh workflow run kernel-packaging.yml -f version=X.Y.Z` (аналогично
   `netlink-packaging.yml`, `tools-packaging.yml`, `rs-packaging.yml`).
3. Поставить тег с префиксом и запушить его:
   ```sh
   git tag kernel-vX.Y.Z && git push origin kernel-vX.Y.Z
   ```
   CI соберёт пакеты и опубликует GitHub Release для этого компонента.

## Архивные репозитории

После проверки монорепо старые репозитории переводятся в архив (read-only) с
README-ссылкой на `ivlev-dev/umbrawg`. Удалять их не нужно: там остаются
открытые PR, issues и feature-ветки, не вошедшие в `master`.

## Откат

Пока монорепо не стал единственной точкой работы, откат — это просто
продолжение работы в старых репозиториях: они не менялись, история и ветки на
месте. Бандлы `handover/backups/2026-11-17/*.bundle` содержат все refs на
момент миграции.
