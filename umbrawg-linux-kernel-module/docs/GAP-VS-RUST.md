# Почему kernel-модуль отстаёт от Rust-демона: статический разбор, гипотезы и план профилирования

Документ по состоянию на 2026-11-23, HEAD `67f8e66d`. Статический разбор
data path и числа v4 (`/root/bench-matrix/v4/results.csv`) — из прохода
2026-11-22; динамика и профиль в §7 сняты на стенде 2026-11-23. Всё, что не
подтверждено измерением, помечено как **оценка**; профиль-план ниже — способ

## 2. Пути по шагам: счётчики syscalls/копий/аллокаций

### 2.1. TX, один bulk-поток, пакет 1420 Б

| Шаг | kernel | Rust |
|---|---|---|
| вход из стека | `ndo_start_xmit` (0 syscalls), GSO-skb до 64 КБ | `read()` из TUN с `IFF_VNET_HDR`+TSO: **1 syscall на ~44 пакета**, `split_gso` режет на 1420 |
| сегментация | `skb_gso_segment`: skb на сегмент, payload в frags (заголовки копируются, payload — нет) | `split_gso` → `bufs[i]`: копия payload каждого сегмента |
| копии payload | 1× в GSO-агрегат (`skb_copy_bits`) + возможная копия в `skb_cow_data`; плюс `skb_checksum_help` читает payload | 2× до шифрования (`split_gso`, `tx_plain`) + 1× в буфер шифрования; **байт скопировано больше, чем у ядра** |
| шифрование | `encrypt_packet`: `skb_cow_data`, sg-список (`skb_to_sgvec`), chacha/AES over sg, `uwg_reset_packet` | `seal_in_place` по одному непрерывному срезу, без sg |
| аллокации | `alloc_skb(headroom + 44×1452)` ≈ **64 КБ (order-4/5) на батч** + 44 `kfree_skb` | 0 на пакет (переиспользуемые буферы) |
| отправка | 1 `udp_tunnel_xmit_skb` на GSO-группу | 1 `sendmmsg` на ≤64 GSO-группы, zero-copy |
| пробуждения | `queue_work_on` crypt-воркера (на цепочку) + `queue_work_on` TX-воркера (на пира) | нет (всё в потоке; `poll`) |

Вывод по TX: дело не в числе копий (у Rust их больше), а в **машинерии
skb**: сегментация, `skb_cow_data`, sg-список, high-order аллокация агрегата,
44 освобождения skb и два пробуждения на батч.

### 2.2. RX, те же 44 пакета в одной GSO-супердатаграмме

| Шаг | kernel | Rust |
|---|---|---|
| underlay RX | veth NAPI → `udp_queue_rcv_one_skb` → **`__udp_gso_segment`: 44 отдельных skb** | veth NAPI → GRO: GSO-skb остаётся целым (`UDP_GRO` на сокете) |
| доставка в туннель | `encap_rcv` **44 раза** (`prepare_skb_header`, lookup, ring) | `recvmmsg`: **1 syscall**, до 64 КБ за датаграмму |
| расшифровка | `decrypt_packet`: `skb_cow_data` (копия payload), sg, chacha/AES | in-place по непрерывному срезу, без sg |
| доставка внутрь | `napi_schedule` на каждый skb → threaded NAPI → `napi_gro_receive` на каждый skb | `RxBatch`: GSO-склейка равных сегментов → **1 `write()` в TUN на ≤64 пакета** |
| аллокации | 44 skb на сегментацию + 44 на расшифровку-копию | 0 |

Главное отличие одной строкой: **ядро проходит полный per-packet путь 44 раза
на одну супердатаграмму, Rust — один раз.** Это же зафиксировано в
[docs/UDP-GRO.md](UDP-GRO.md) и в гейте S3
([PEER-PATH-SHARDING.md](PEER-PATH-SHARDING.md)): на 2 Гбит/с один CPU уже
показывал 100% с 62.9% softirq veth.

Измерение §3 уточняет картину: сама сегментация в этой цепочке дешёвая
(~1% циклов), дорога per-packet работа, которая выполняется уже после неё.

## 3. Куда уходит CPU: измерение (perf, 12 с, 1 и 5 пиров)

`perf record -a -F999` на base HEAD, симв. модуля резолвятся. В профиле
~10–11% сэмплов — сам `bpftrace` (в p5 ещё 3.7% посторонний `clang`),
поэтому доли ниже нормализованы. Числа — проценты циклов, не «доля
разрыва».

| Стадия | 1 пир | 5 пиров | Комментарий |
|---|---:|---:|---|
| шифр: `chacha_8block_xor_avx2` + `poly1305_blocks_avx2` + `chacha20poly1305_crypt_sg_inplace` | **21.0%** | **21.3%** | главная статья; arch-символы видны |
| skb alloc/copy/segment (`__alloc_skb`, `prep_new_page`, `memset`/`memcpy`, `skb_segment`) | **11.3%** | **15.5%** | `skb_cow_data` — ~2 раза на пакет |
| — в том числе вся RX-GSO-цепочка | ~1.0% | ~1.4% | `__udp_gso_segment` 0.03/0.08% raw, `skb_segment` 0.75/1.08%, аллокации сегментов |
| clock/timer/sched (`mod_timer` ~1.1 на RX-пакет — старый keepalive, 2 workqueue-хопа) | 11.4% | 7.8% | |
| локи | 4.8% | 3.3% | |
| jhash | 2.2% | 2.4% | |
| net core | 7.2% | 5.9% | |
| код модуля `uwg_*` | 5.5% | 5.6% | |

По потокам: p1 — воркеры модуля 64% + NAPI модуля 16% = **80% CPU**,
`iperf3` 8.7%; p5 — 63% + 12.5%, `iperf3` 10.3%. Счётчики стадий (bpftrace,
12 с): `uwg_rx` 3.79M/6.49M, `rx_gso_split` 85.6k/210.6k (2.3%/3.2% — ровно
1/44), `skb_cow_data` 7.66M/12.9M (~2 на пакет), `gro_receive` 3.89M/6.42M
(per-packet, не батчем), `queue_work_on`/`try_to_wake_up` 2.30M/2.23M и
1.75M/2.07M. Inclusive: `uwg_packet_tx_worker` 28.6/29.2%,
`uwg_packet_decrypt_worker` 17.8/16.6%, `uwg_packet_encrypt_worker`
14.8/14.6%, `__napi_poll` 27.4/25.9%.

**Гипотеза о RX-GSO опровергнута:** полная цепочка сегментации — ~1–1.5%
циклов при пороге >15%, который закладывался в план. Сегментация дешёвая
(frags шарятся), а per-packet работа после неё — decrypt, `skb_cow_data`,
encap, deliver — всё равно выполняется на каждый туннельный датаграм. Даже
идеальный GRO снимет ~1–1.5%, а не 40–55%.

Косвенное подтверждение роли шифра остаётся: AES (в 2.7 раза быстрее) даёт
ядру +10.8% на 1 пире, +15.8% на 5 и +29% на 50 — но при 50 пирах, где
параллелизм уже есть, вклад шифра в **относительный** разрыв растёт (Rust на
AES тоже ускоряется, но меньше — упирается в другое).

## 4. Корневые причины

- **R1. Нет GRO на underlay-сокете — необходимое, но не главное.** Encap-сокет
  не получает GSO-skb: `udp_queue_rcv_one_skb` режет супердатаграмму на
  сегменты до `encap_rcv`. Rust ставит `UDP_GRO` на обычный UDP-сокет и
  получает супердатаграмму целиком; из модуля это не лечится
  (`udp_gro_receive`/`udp_gro_complete` не экспортируются). Измеренный
  потолок самого GRO — **~1–1.5% циклов** (§3): без батчевого decrypt и
  единого write в TUN он не даёт паритета.
- **R2. TX-агрегация копированием.** Зашифрованные skb копируются в новый
  order-4 skb и освобождаются. Rust шифрует сразу в буфер отправки.
- **R3. Модель «один skb — один шаг конвейера» (главная причина по
  измерению).** На RX: сегментация → encap
  → ring → decrypt → NAPI. На TX: xmit → ring → encrypt → TX-воркер. У Rust
  на 44 пакета: 1 read + 44 in-place decrypt + 1 write / 1 read + 44 encrypt
  + 1 sendmmsg. Именно из-за этой модели после дешёвой сегментации (~1%)
  остаются дорогие decrypt, `skb_cow_data` (~2 на пакет) и encap — 11–15%
  циклов на skb-машинерию плюс 21% на шифр.
- **R4. Шифр.** Транспорт идёт через `chacha20poly1305_*_sg_inplace` из
  `lib/crypto` (≈12 Гбит/с на ядро на этом стенде); arch-ускорение chacha в
  ядре есть (`CONFIG_CRYPTO_LIB_CHACHA_ARCH=y`, видны
  `chacha_*_xor_avx2/avx512`), но **AEAD-шаблона с SIMD в этой сборке нет**
  (`arch/x86/crypto/chacha20poly1305-simd` не собран), поэтому «перевести
  ChaCha на Crypto API, как AES» даст не ускорение, а лишний sg-слой.
  Транспортный AES-256-GCM через Crypto API (AES-NI/VAES, 33 Гбит/с) в
  2.7 раза быстрее — но это смена шифра, а не оптимизация ChaCha.
  Какая реализация реально вызывается, показывает
  `@chacha[...]` в `perf-gap.sh` (ssse3 / avx2 / avx512vl).
- **R5. Мелкие per-packet расходы.** `uwg_ext_maybe_send_caps()` (ktime +
  spinlock) на каждый расшифрованный пакет и арм/снятие keepalive-таймера на
  пакет — **оба уже убраны** гейтом CAPS и коалесингом keepalive
  (`67f8e66d`). Остаются `get_cpu()/put_cpu()`, `atomic64_add` статистики,
  `skb_cow_data`, `uwg_reset_packet`.

## 5. Гипотезы

Ожидаемый выигрыш — **оценка** до профиля; «решает» — какой символ/счётчик
подтверждает или убивает гипотезу.

### P1 — то, что может закрыть разрыв на 1–10 пирах

| # | Гипотеза | Ожидание | Стоимость/риск | Решает |
|---|---|---|---|---|
| P1-0 | **Батчевый конвейер RX/TX**: один GSO-read + batch decrypt + один `write()` в TUN; на TX — шифрование сразу в агрегат (P1-3 как часть) | единственный путь к паритету: убирает два `skb_cow_data` на пакет и per-packet хопы | XL / M (переделка R3, меняет транспорт приёма) | распределение §3: шифр 21%, skb 11–15%, `skb_cow_data` ~2/пакет, 2 `queue_work_on` на батч |
| P1-1 | **UDP GRO на underlay** (патч ядра: экспорт `udp_gro_receive`/`udp_gro_complete`/`udp_read_skb` + приём обычным UDP-сокетом с `UDP_GRO`, как в прототипе `UDP-GRO.md`) | измеренный потолок **~1–1.5%**; сам по себе паритета не даёт, нужен как вход P1-0 | L / M (меняется транспорт приёма, нужен fallback) | доля `__udp_gso_segment` + `skb_segment` + `__alloc_skb` в softirq > 15% — **не подтвердилась** (~1%) |
| P1-2 | **Повторить проверку «обычный сокет + UDP_GRO» без патча ядра** (прототип не получил GSO-skb; возможно, дело в способе включения, а не в отсутствии экспорта) | если GRO включится — тот же потолок ~1–1.5%, без патча | M / M | `skb_is_gso()` на входе `__skb_recv_udp`, `gro_enabled` в сокете, счётчик `udp_gro_receive` |
| P1-3 | **Zero-copy TX-агрегация**: шифровать сразу в слот GSO-skb (сгруппировать до шифрования, паддинг батча как в Rust), убрать `skb_copy_bits`+`kfree_skb` | +2…5% на TX-ядре; на 1–10 пирах +1…3% общего | M / M | доля `uwg_packet_gso_alloc`+`skb_copy_bits`+order-4 `__alloc_skb`+`__kfree_skb` в TX-воркере > 5% |
| P1-4 | **AES-GCM по умолчанию при наличии AES-NI** (политика/автовыбор, не код data path) | +11% (1 пир), +16% (5), +29% (50) — уже измерено | S / L (совместимость: шифр должен совпадать у пиров) | — (числа есть) |
| P1-5 | **Изоляция CPU модуля** (scratch-сборка `worker_cpus`, в продукт не идёт): per-peer TX-воркер сейчас выбирается round-robin по **всем** online CPU (`peer->internal_id % online`), а его CPU определяет и CPU underlay-RX-softirq; при 5 пирах ids 4–5 попадают на CPU 4–5, где живёт iperf3, тогда как Rust-демоны закреплены на 0–3 | не ускорение само по себе, а честный A/B + продакшн-изоляция | S / L | `perf`: доля `uwg-*`/`ksoftirqd` на CPU 4–5 при `worker_cpus=0-3` = 0 |

### P2 — микро, по 1–3% каждое

| # | Гипотеза | Ожидание | Статус |
|---|---|---|---|
| P2-1 | Гейт `uwg_ext_maybe_send_caps()` на RX-пути (ktime+spinlock на пакет при выключенном расширении) | +1…3% на RX-ядре | **сделано** |
| P2-2 | Коалесинг keepalive-таймера: `uwg_timers_any_authenticated_packet_sent()` снимает таймер на каждый батч, `uwg_timers_data_received()` армит на **каждый** пакет → один `mod_timer` на пакет. Переармировать на TX-батче и не трогать на RX | +1…2% | **сделано** (`67f8e66d`), soak пройден; интерливный A/B 50 пиров +2.8% (keepalive-only +5.8%) |
| P2-3 | `gso_segs_max` (44 → 46 / 24 / 8): проверка гипотезы «order-4 аллокация дорога» | 0…2% | **ручка добавлена** |
| P2-4 | Убрать `get_cpu()/put_cpu()` из `uwg_queue_enqueue_per_device_and_peer()`: все вызывающие уже под `rcu_read_lock_bh()` (preempt_count ≠ 0) | +0.5…1% | кандидат, риск на PREEMPT_RT |
| P2-5 | `uwg_ext_peer_extension()` (проба 8 байт заголовка) на каждый пакет при выключенном расширении — сэмплировать/взять под тот же гейт | <0.5% | кандидат |
| P2-6 | Один `napi_schedule` на дренаж ring вместо одного на skb | <0.5% | кандидат |
| P2-7 | `UWG_TX_MAX_ENTRIES` (48) / размер батча TX-воркера | 0…1% | ручка есть |

### Что проверено и **не** поможет

- **Дробить TX-цепочку на несколько ring-записей** (чтобы single-flow шифровался
  на нескольких CPU): не поможет, потому что TX-воркер у пира **один**, и
  underlay-RX-softirq всё равно останется на одном CPU (том, где работает
  TX-воркер). Распараллелится только шифрование, а оно не насыщено
  (~5.6% бокса в гейте S3).
- **Round-robin ring на цепочку** (P0-3), **inline-обработка при пустой
  очереди** (P0-4), **TX-коалесинг пробуждений**, **отключение threaded
  NAPI**, **wire-correct** (по датаграмме на пакет), **S2 (per-flow RX
  шарды)** — уже измерены и отклонены, см. `docs/PERFORMANCE.md`
  и `TODO.md`. Не повторять без новых данных профиля.
- **`worker_cpus` (scratch) ≠ ускорение**: это инструмент изоляции, в продукте его нет. Если после него
  ядро станет **медленнее**, значит v4-числа были завышены за счёт iperf3-CPU.

## 6. План профилирования

Готовый харнесс: `src/tests/perf-gap.sh` (запускать на стенде под root, пока
идёт прогон; сам трафик не создаёт). Он снимает:

1. `perf record -a -g` (999 Гц) + отчёты по символам, по `comm`, по DSO,
   `perf annotate` для топ-символов и (если установлены
   `stackcollapse-perf.pl`/`flamegraph.pl`) `flamegraph.svg`.
2. `perf stat -a` (cycles, instructions, IPC, context-switches,
   cpu-migrations, page-faults) до/во время/после.
3. `bpftrace`-счётчики и гистограммы (см. таблицу ниже).
4. Снимки `softnet_stat`, `/proc/softirqs`, `nstat -az`, `vmstat`, `slabtop`,
   `ss -ti` (RTT), `/proc/net/udp` (rmem), `ethtool -S` veth.

Ключевые точки и что они доказывают:

| Точка | Что считаем | Гипотеза |
|---|---|---|
| `__udp_gso_segment`, `udp_queue_rcv_one_skb`, `skb_segment`, `__alloc_skb`/`__kfree_skb` (caller = udp/veth) | число сегментаций на супердатаграмму и их цена | R1/P1-1 |
| `udp_gro_receive`, `skb_is_gso` на входе сокета | работает ли GRO вообще | P1-2 |
| `uwg_packet_receive` (entry/exit, гистограмма ns) | цена encap-пути на пакет | R3/R5 |
| `uwg_packet_rx_poll` (entry/exit, бюджет) | цена NAPI-диспетчера на пакет, размер батча | R3 |
| `uwg_packet_send_staged_packets` (entry/exit) | цена сборки батча | R3 |
| `uwg_packet_gso_alloc`, `skb_copy_bits`, `__alloc_skb` (caller = uwg) | копия + order-4 аллокация | R2/P1-3 |
| `uwg_packet_encrypt_worker`/`decrypt_worker` (busy time) | загрузка шифра | R4 |
| `chacha20poly1305_*_sg_inplace`, `chacha_*_xor_*` (ssse3 / avx2 / avx512vl) | какая реализация ChaCha реально работает | R4 |

**Порядок прогонов** (каждый — 2× по 15–20 с, медиана):

1. `kernel, 1 пир` и `kernel, 5 пиров` — полный профиль (perf + bpftrace).
2. `kernel, worker_cpus=0-3` — тот же прогон: проверка P1-5.
3. `kernel, 50 пиров` — только perf (`perf record -a`), bpftrace уже дорог.
4. `kernel, AES, 1 пир` — сравнение доли crypto-символов (R4).
5. `rust, 1 пир` и `rust, 5 пиров` — те же perf-отчёты для эталонного
   профиля (там видно, сколько стоит `recvmmsg`/`write`/крейт).

**Пороги решений:**

- `__udp_gso_segment`+`skb_segment`+`__alloc_skb` (RX) > 15% циклов на
  RX-CPU → P1-1/P1-2 в приоритете, остальное не даст больше 5%.
- `uwg_packet_gso_alloc`+`skb_copy_bits`+order-4 `__alloc_skb`+`__kfree_skb` в
  TX-воркере > 5% → P1-3.
- `uwg_packet_encrypt_worker` busy > 50% одного ядра при ChaCha → R4
  (и только тогда имеет смысл думать про ChaCha-политику/AES).
- `ktime_get`/`mod_timer`/`_raw_spin_lock` с caller `uwg_*` > 3% → P2-1/P2-2.
- `queue_work_on`+`try_to_wake_up` > 5% → P2-6/P2-7.
- `skb_cow_data`/`pskb_expand_head` > 5% → отдельная гипотеза о копиях в
  decrypt/encrypt.

**Фактический результат (2026-11-23, §3):** порог RX ниже в 15 раз —
вся цепочка ~1–1.5%, поэтому P1-1/P1-2 сами по себе не дают паритета;
`skb_cow_data` — ~2 вызова на пакет, skb-машинерия 11–15%; крипто 21%;
`queue_work_on`/`try_to_wake_up` 2–4% (2 хопа на батч). Приоритет перешёл
к P1-0.

## 7. Патчи, применённые в этом проходе

Сборка проверена (`make LLVM=1`, `make LLVM=1 module-debug`), selftest
`FEC 1..44` и `queueing 1..17` проходят, выгрузка чистая. CPU-маски в
продукте **нет**: `worker_cpus` остался только в scratch-копии, в продукт
маски не идут по требованию пользователя.

Замеры — один стенд, 10–15 с на ячейку: `TUNNEL_CPUS=0-3`,
`IPERF_CPU=4-5`. Ниже — четыре патча одного прохода; «доля от Rust» —
throughput патченной сборки относительно Rust на том же стенде.

| Пиров | base HEAD | +4 патча | Rust | доля от Rust |
|---:|---:|---:|---:|---:|
| 1 | 4.56 (4.44–4.65) | 4.55 (4.24–4.71) | 5.84 | 78% |
| 5 | 6.64 (n=8) | 6.62 (n=7) | 10.64 | 62% |
| 50 | 8.09 (n=2) | 8.33 (7.73–8.78, n=4) | 9.46 | 88% |
| CPU %, 1/5 пиров | 52/75 | 52/76 | 33/65 | — |

Контрольный interleaved A/B на тех же ячейках: 1 пир — 4.60 против 4.60,
5 пиров — 6.50 против 6.61. На уровне сборки патчи по throughput нейтральны;
эффект виден в локальных A/B — +4% на 1 пире у CAPS-гейта, падение дропов и
RTT у классификации.

1. **Порядок классификации: transport первым** (`receive.c`,
   `uwg_determine_type_and_padding()`). При `RandomTrailers` каждый тип
   проверяется с ослабленным `>=`, поэтому data-пакет сравнивался с
   диапазонами control-типов по чужому offset и случайно в них попадал.
   Замер: старая раскладка — **72 пакета ушли в handshake-путь** на 4.49M
   принятых, новая — **0** на 4.44M. На 5 пирах медиана RTT упала с
   0.48–0.53 мс до 0.10–0.22 мс.
2. **Гейт CAPS на RX-пути** (`peer.h`: `uwg_peer_caps_may_send()`,
   `receive.c`). `uwg_ext_maybe_send_caps()` вызывался на каждый
   расшифрованный пакет и брал `ktime_get()` + `spin_lock_bh()` даже при
   выключенном расширении. Предикат — точное объединение условий, при
   которых callee может что-то отправить, поведение не меняется. 1 пир —
   4.60 против 4.43 (+4%), 5 пиров — паритет.
3. **Коалесинг keepalive-таймера** (`timers.c`, `peer.h`). Было:
   `timer_delete()` на каждый TX-батч; после него следующий принятый пакет
   видел таймер снятым и армил его заново, то есть `mod_timer` на пакет.
   Стало: таймер остаётся взведённым, expiry сравнивает `last_data_tx`
   (обновляется только реальными кадрами) с `keepalive_armed`. Семантика
   сохранена: downlink без наших данных шлёт keepalive раз в
   `keepalive_timeout`, поток с ACK/data — не шлёт. На 1 пире число
   `mod_timer` не изменилось — источник не keepalive, а
   `uwg_packet_cwnd_arm_retry()` и TCP. Поля вынесены из cacheline с
   `is_dead` (первая версия дала −7% на 50 пирах из-за false sharing;
   после переноса к таймерам — паритет/лучше). Soak (idle 180 с,
   downlink-only, rekey каждые 15 с, 50 пиров): на проводе поведение
   совпадает с base — keepalive раз в timeout при простое, ≈0 при
   трафике; 0 дропов, dmesg чистый. Интерливный A/B 50 пиров: медиана
   +2.8% при разбросе ±7%, вариант «только keepalive» — +5.8% (все пять
   пар положительные).
4. **`gso_segs_max`** (`send.c`, 1…46, default 44) — ручка A/B размера
   GSO-агрегата, дефолтное поведение не меняется. A/B на 1 пире: 44 → 4.63,
   16 → 4.16–4.33, 8 → 4.41, 2 → 3.34, 1 → 3.74; на 5 пирах: 44 → 6.94,
   1 → 5.70. 44 — оптимум на стенде.

Раздельные пороги work stealing (4/32/128 skb) проверены отдельно: выигрыша
нет ни в TX, ни в RX, оставлено общее значение `UWG_CRYPT_STEAL_THRESHOLD` = 4.

### Почему на 5 пирах всё ещё −38%

Scratch-сборка с CPU-маской воркеров на 0–3 даёт на 5 пирах **8.43 Гбит/с
(+27%, CPU 91% против 76%)**. То есть разрыв с Rust на 5 пирах — в основном
методическая асимметрия стенда: bound-воркеры модуля выбираются round-robin
по **всем** online CPU (см. §9), поэтому часть пиров попадает на CPU 4–5, где
busy-loop'ит iperf3. Это одновременно и продакшн-риск: без изоляции CPU модуль
конкурирует с чужой нагрузкой за те же ядра. CPU-маски в продукт **не идут** —
пользователь запретил, `worker_cpus` остаётся только в scratch-копии.

### Почему на 1 пире −22%: per-packet конвейер

Профиль 1 пира: `udp_queue_rcv_skb` 8%, `__skb_gso_segment` 8%, `skb_segment`
7.5%, `__alloc_skb` 5.8%, crypto — 20–32%. Шифр не доминирует: основное —
сегментация underlay, аллокации и encap на каждый пакет. Rust тратит на ~35%
меньше CPU, потому что его конвейер батчевый: `recvmmsg` + `UDP_GRO` на входе,
`sendmmsg` на выходе, без per-packet skb-аллокаций и без `skb_gso_segment` в
softirq.

### GRO для encap: проверено и не работает на 7.3.4

- `udp_allow_gso()` (флаги `ACCEPT_L4|ACCEPT_FRAGLIST`, 0x30/0x70) —
  encap по-прежнему получает по одному сегменту, `__udp_gso_segment`
  вызывается на каждую супердатаграмму;
- `udp_tunnel_update_gro_rcv()/udp_tunnel_update_gro_lookup()` — ставят
  `GRO_ENABLED`, но `gro_receive` остаётся NULL;
- `udp_tunnel_sock_cfg.gro_receive/gro_complete` — не помогают;
- `udp_gro_receive`/`udp_read_skb`/`__skb_recv_datagram` **не экспортированы**.

При этом в userspace обычный UDP-сокет с `UDP_GRO` над тем же veth получает
**200/200 датаграмм по 62480 Б** (44 сегмента) — механизм рабочий.
Эквивалент GRO = приём обычным UDP-сокетом + `UDP_GRO` + `recvmsg` в
kthread, с payload-only разбором и сборкой skb на пакет (~300–400 строк).
Это необходимое, но недостаточное условие целей `single ≥5` / `5 пиров ≥8`:
по измерению (§3) сам GRO даёт ~1–1.5%, паритет требует ещё батчевого
decrypt и единого `write()` в TUN (P1-0).

### Вывод прохода

Минимальные правки безопасны и приняты: регрессий по throughput нет (1 и 5
пиров — паритет с контролем; 50 — интерливный A/B из 6 пар дал +2.8% при
разбросе ±7%, keepalive-only +5.8%), дропы и RTT лучше.
Цели `5` / `8` / `8` Гбит/с не закрыты: 4.55 и 6.62 далеки от цели, 50
пиров дают 7.6–8.3 в зависимости от сессии. Дальше — проект P1-0 (батчевый
конвейер), в котором GRO на underlay — только вход: сам он по измерению
даёт ~1–1.5%.

## 8. Дизайн двух крупных патчей

### 8.1. UDP GRO на underlay

Сам по себе патч измеренного разрыва не закрывает (§3): GRO — необходимый
вход батчевого конвейера P1-0, а не замена ему.

Два варианта, оба уже описаны в [UDP-GRO.md](UDP-GRO.md):

- **С патчем ядра**: `EXPORT_SYMBOL_GPL(udp_gro_receive)`,
  `EXPORT_SYMBOL_GPL(udp_gro_complete)`, `EXPORT_SYMBOL_GPL(udp_read_skb)`;
  в модуле — обычный UDP-сокет + `UDP_GRO` + `sk_data_ready` →
  `__skb_recv_udp`, GSO-skb разбирается `__skb_gso_segment` (или отдаётся
  целиком в существующий `uwg_packet_receive` после `skb_push` UDP-заголовка).
  Kconfig-опция с runtime-fallback на encap-путь, если символов нет.
- **Без патча**: повторить прототип, но с диагностикой (`bpftrace`:
  `skb_is_gso`, `gro_enabled`, `udp_gro_receive`); если GRO включается —
  оставить, если нет — вариант выше единственный.

Что важно не сломать: roaming (endpoint по источнику), несколько
`extra_ports`, порядок внутри пира (сейчас его держит `prev_queue` пира;
при батчевом приёме порядок надо сохранить той же очередью), FEC-шарды
(они тоже приходят GSO-группами).

### 8.2. Zero-copy TX-агрегация

Сейчас: `staged → encrypt (in place) → TX-воркер → группировка по длине →
alloc_skb(64 КБ) + skb_copy_bits ×N → send → kfree_skb ×N`.

Цель: `staged → группировка по длине → alloc_skb(64 КБ) → encrypt сразу в
слот → send`.

Точки изменения:

- `uwg_packet_send_staged_packets()` уже знает все длины и `ds` до
  шифрования; паддинг для full-MTU пакетов равен 0, для коротких — его можно
  выбрать **один на группу** (как `batch_padding` в Rust) и передать в
  шифрование через `PACKET_CB(skb)->padding` (механизм уже есть для
  control-кадров, см. комментарий в `encrypt_packet()`).
- `encrypt_packet()` получает «целевой буфер + смещение» (или skb-слот) и
  пишет туда header+payload+tag; `skb_cow_data`/`skb_cow_head` для исходного
  skb не нужны — только чтение plaintext.
- `uwg_packet_create_data_done()` перестаёт копировать: собирает `skbs[]` из
  уже зашифрованного агрегата и отправляет один skb; освобождаются только
  исходные (пустые) skb.
- FEC-шарды и `pace_len` уже сгруппированы по одинаковой длине
  (`uwg_fec_shard_tail`), так что ограничение «одна группа — один `ds`/`m`»
  сохраняется.

Риски: `skb_cow_data` сейчас же и «материализует» данные, на которые
ссылаются frags; при шифровании в чужой буфер нужно аккуратно читать
исходный skb (`skb_copy_bits` во временный буфер был бы той же копией —
значит, нужен прямой доступ к frags/linear части). Поэтому патч стоит делать
после профиля: если `skb_copy_bits` в TX-воркере окажется < 3%, выигрыш не
окупит риск.

## 9. Методические замечания к стенду

- **Пиннинг несимметричен**: Rust-демоны сидят на `TUNNEL_CPUS=0-3`, а
  bound-воркеры модуля — на всех online CPU (0–5). `worker_cpus=0-3`
  выравнивает условия; без этого сравнение «Rust на 4 CPU против ядра на 6»
  скорее льстит ядру, но загрязняет iperf3 на 4–5.
- **RPS выключен** (`RPS_MASK=off`): multi-queue veth не раскладывает RX по
  CPU. Для одиночного потока RPS и не поможет (один hash), для 5–10 пиров
  стоит проверить `RPS_MASK=0x30` отдельной серией — но это меняет
  методику, поэтому только как отдельный A/B, не в основную матрицу.
- **UDP-ячейки** (400 Мбит/с) не различают реализации; для UDP-потолка нужен
  `UDP_RATE=0` (без лимита) и контроль `RcvbufErrors` у iperf3.
- **`gso_segs_max`** позволяет отделить «дорогую order-4 аллокацию» от
  «дорогой сериализации GSO»: если 8 сегментов не хуже 44 — аллокация
  значима; если хуже — важнее число underlay-датаграмм.

## 10. Что делать в первую очередь

1. Профиль снят: RX-GSO-гипотеза **опровергнута** (~1–1.5% циклов);
   причина — шифр 21%, skb-машинерия 11–15% (два `skb_cow_data` на пакет)
   и per-packet модель конвейера (2 `queue_work_on` на батч).
2. Главный путь к паритету — **P1-0**: батчевый конвейер (один GSO-read,
   batch decrypt, один `write()` в TUN) с GRO как входом, а не отдельный
   GRO-патч.
3. Параллельно — P1-3 (zero-copy TX) как часть P1-0 и P2-4 (микро).
4. `gso_segs_max` A/B сделан: default 44 — оптимум (16 → −7.7% на 1 пире);
   `worker_cpus=0-3` — только в scratch-сборке, для изоляции профиля.
5. Шифр: на этой платформе AES-GCM быстрее (измерено), ChaCha оставить
   fallback'ом. Отдельного SIMD-AEAD-шаблона ChaCha в этой сборке ядра нет,
   так что «ускорить ChaCha в модуле» без смены шифра нечем — это вопрос
   политики/конфигурации, а не патча data path.
