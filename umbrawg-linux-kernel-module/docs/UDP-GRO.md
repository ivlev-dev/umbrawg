# UDP GRO для UmbraWG: замеры, блокер и патч ядра

Документ фиксирует результаты исследования UDP GRO для data path ядра
UmbraWG по состоянию на 2026-11-19. Прототип в модуле откачен; в master
остались только выводы. Rust-демон использует собственный userspace-путь
и к этому документу не относится.

## 1. Зачем

Внешний UDP-поток одного пира в ядре сегментируется в `udp_rcv_segment`
и обрабатывается `encap_rcv` на каждый сегмент в softirq. Один CPU
(RPS) упирается в 100%, поэтому 3c/10 у ядра ~4.4 Гбит/с против ~4.6–4.8
у `go`, который батчирует приём в userspace.

## 2. Userspace-проверка механики

Тест: обычный UDP-сокет, отправитель с `UDP_SEGMENT` (32 сегмента по
1420), получатель с `UDP_GRO`, loopback. Исходник:
`.local/bench/udp-gro/udp_gro_test.c`.

| Режим | recv-вызовов на отправку | maxrecv | Mbit/s |
|---|---:|---:|---:|
| без `UDP_GRO` | 32.0 | 1420 | 11 466 |
| с `UDP_GRO` | **1.0** | 45 440 | **37 519** |

Механика положительная: в 32 раза меньше вызовов и в 3.3 раза выше
throughput. Это верхняя оценка выигрыша для батчированного приёма.

## 3. Прототип в модуле

Что сделано (откачено, ветка эксперимента):

- устройство создаёт **обычный** UDP-сокет (`udp_sock_create`, без
  `setup_udp_tunnel_sock`), а не encap-сокет;
- `SO_RCVBUF` 16 МиБ, `UDP_GRO` через `udp_prot.setsockopt(...)`;
- `sk_data_ready` → workqueue; приём через **`__skb_recv_udp`**
  (экспортируется, обслуживает `reader_queue` и освобождает rmem);
- GSO-skb разбирается `__skb_gso_segment`, сегменты отдаются в
  существующий `uwg_packet_receive`; UDP-заголовок возвращается
  `skb_push` перед разбором.

Результат: handshake, ping и TCP-данные работают, туннель стабилен,
3c/10 ≈ **4.4 Гбит/с**. То есть обычный UDP-сокет + `__skb_recv_udp`
как транспорт приёма работоспособен.

## 4. Блокер: GRO не включается

- `udp_prot.setsockopt(sk, SOL_UDP, UDP_GRO, ...)` возвращает **0**, но
  `udp_sk(sk)->gro_receive` остаётся **NULL**;
- в приёмнике **нет GSO-skb**: на всех пакетах `skb_is_gso() == 0`;
- колбэки GRO `udp_gro_receive`/`udp_gro_complete` в работающем ядре
  7.3.4 — локальные символы (`t`), без `__ksymtab_`, поэтому назначить
  их из модуля нельзя;
- `udp_read_skb` тоже не экспортируется (но его логику заменяет
  экспортируемый `__skb_recv_udp`).

Итог: без правки ядра коалесинг недоступен; обычный сокет даёт лишь
альтернативный (не encap) приём без выигрыша по softirq.

## 5. Предлагаемый патч ядра

Минимальный вариант (GPL-экспорт, без изменения поведения):

```c
EXPORT_SYMBOL_GPL(udp_gro_receive);
EXPORT_SYMBOL_GPL(udp_gro_complete);
EXPORT_SYMBOL_GPL(udp_read_skb);
```

Дополнительно можно добавить helper включения GRO для kernel-сокета
(чтобы не вызывать `udp_prot.setsockopt` напрямую).

В модуле:

- новая Kconfig-опция `UMBRAWG_UDP_GRO`, `depends on` наличия экспорта
  (проверка при сборке через `IS_ENABLED`/`MODULE_SYMBOL` или
  `crypto_has_aead`-подобный runtime-чек);
- при наличии — обычный UDP-сокет + GRO + workqueue (как в прототипе);
- иначе — текущий encap-путь, без изменений.

Ожидание: снятие per-segment softirq-нагрузки, рост 3c/10 до уровня
`go` и выше; на ARM/мобильных — дополнительный запас.

## 6. Альтернативы без патча

- несколько внешних UDP-потоков на пира: **реализовано** через
  per-device `extra_ports` (0…8, по умолчанию 0; netlink/UAPI/конфиг):
  базовый + N эфемерных encap-сокетов, round-robin отправка, приём на
  всех; см. PERFORMANCE.md. Даёт паритет с `go` на obf0 и плюс на obf1;
  меняет SourcePort/roaming.
- zero-copy TX: `skb_shift` не экспортируется; альтернатива —
  шифровать сразу в слот GSO-агрегата (переделка data-path, 2–5%);
- оставить encap-путь и оптимизировать batching/очереди (сделано:
  GSO 32, очереди 8192, RPS 0x30).
