  паритет. Держать `off` по умолчанию, с FEC не включать.
- UDP: без FEC потери повторяют `netem` (±0.4 п.п.), с FEC `2:1` остаётся

- Multi-peer (ChaCha, obf off): 5 пиров — 6.892 Гбит/с, fairness 1.10, CPU 91%;

- Потери 2%, 5 пиров: `uwg-kernel` AES 1.627 / mixed 1.421 Гбит/с против

### Почему 3 соединения не растут

Один пир = один внешний UDP-сокет + один threaded NAPI-поток + одна in-order
очередь. Параллелится только крипта (per-CPU воркеры), приём из сокета и TX
идут последовательно на пира. RPS/XPS на veth в замерах выключены. Замеры
1/2/4 пиров подтверждают: узкое место — per-peer NAPI, а не сокет.

### Отклонено, не мержить

- **P0-3** (`get_cpu` вместо round-robin выбора CPU): −12…−26% TCP, UDP-потери
  до 10%, ретрансмиты ×1.6. Причина — крипта перестаёт размазываться по CPU.
- **P0-4** (inline-обработка при пустой очереди, ветка `feature/perf-final`):
  те же −12…−26% TCP, потери до 10%, ретрансмиты ×1.6. Причина — RX попадает
  внутрь TX-воркера.
- **TX-коалесинг** (второй `pending`/`queue_work_on` на TX-очередь пира,
  `feature/wakeup-batch-tx`): UDP без лимита −4…−6%, 17/20 парных прогонов
  отрицательные.
- **Отключение threaded NAPI**: −11…−13% TCP.
- **Ветка `wire-correct`** (по одной датаграмме на пакет): −36…−41%.
- **S2: пул RX-шардов на устройство** (`feature/rx-shards`, per-flow доставка):
  `3c c10` +6.6% (K=2, obf0) / +5.2% (K=4, obf1), в отдельных ячейках до −8.8%.
  Цель +50% не достигнута: диспетчер пира (prepare, timers, allowedips, trim)
  остаётся последовательным. Ветка оставлена как эксперимент, в master не
  влита. Замеры: `handover/artifacts/S2-RESULTS-2026-11-17.md`.

### В работе

- **Per-peer ёмкость** — S3 (шардирование полного пути после replay) прошёл

  насыщен на 100% входным softirq veth. Дизайн и цифры —

- Полная матрица (1/2/4/5/10/50 пиров × соединения × потери × MTU ×

## Сборка и проверка

```sh
cd src
make LLVM=1            # обязательно для ядер, собранных clang (Arch/CachyOS)
sudo insmod umbrawg.ko
sudo ip link add dev uwg0 type umbrawg
sudo ip link del uwg0
sudo rmmod umbrawg
```

`srcversion` не годится для проверки пересборки: при правках только в
заголовках он не меняется. Смотрите время `.ko` или лог сборки.

Debug-сборка с селфтестами (allowedips, counter, ratelimiter):

```sh
make module-debug LLVM=1
```

Проверка netlink-паритета 3.1:

```sh
src/tests/netlink-parity.sh
```

## Что работает

- Noise IK, cookie, rekey/keepalive/reject-таймеры.
- Обфускация 3.1: `H1..H4`, `S1..S4`, `Jc/Jmin/Jmax`, `I1..I5`, header protection,
  `ContentPaddingAddition`, `RandomTrailers`, `DisableCookies`.
- GSO на отправке (стандартный UDP GSO, jumbo до 23 КБ) и GRO на приёме TUN,
  per-CPU крипто-очереди.
- Interop GSO-агрегации с `go`, `rust` и `amneziawg` проверен в обе стороны,
  фрагментов на проводе 0.
- Совместимость с userspace-демоном `umbrawg` (Rust) в обе стороны, с обфускацией и без.
- BBR-гейт: пейсинг/`inflight`/`cwnd` включаются только при `ACK` в CAPS
  пира; без ACK трафик не шейпится, пиры видны как `peers_no_ack`
  (атрибут 9, `uwg show bbr-stats` печатает `peers_no_ack`). Loss-порог
  у обоих 20% раунда.
- Partial FEC parity: `FEC_PARTIAL` (бит 4) включает `k' = n`, `m' = m`
  для неполных блоков; без флага — legacy `m' = 0`. Sparse ping при 2%
  потерь: 3–6% → 0–0.5%.

## Известные проблемы

- Версии упаковки согласованы на `0.4.1` (`0.4.1` в RPM `Version`):
  `src/version.h`, `src/Makefile`, `src/dkms.conf`, `debian/changelog`,
  `umbrawg-dkms.spec`. Перед тегом остаётся `updpkgsums` в `contrib/arch/`.
- Если инициирует ядро, первая попытка handshake теряется, когда userspace-демон
  ещё не забиндил UDP-порт; соединение поднимается на ретрае через 5 с. Порядок
  настройки: сначала userspace, затем ядро.
- `make` без `LLVM=1` на clang-ядрах падает на флагах (`-fms-anonymous-structs` и др.).
- Поддержка 6.x и старее сознательно удалена.
- UDP GRO на сокете модуля отсутствует (`gro_receive = NULL`, `ACCEPT_L4` не
  выставлен); оценка выгоды 2–4% для одиночного пира — гипотеза, не измерено.
- Полная матрица снята до 50 пиров (5/10/50); 100 не тестировались по
  решению — у Rust прогноз ~4.3 ГБ. На 50 пирах модуль теряет 36% к 10 пирам
  при fairness 9.1, см. п. 2 ниже.
- UDP-потери в замерах — переполнение приёмного буфера `iperf3`
  (`RcvbufErrors`), а не дропы туннеля; в diag стенда есть `QUEUES`/`RPS` и
  счётчики фрагментации.

## Что делать дальше (по приоритету)

1. **Per-peer ёмкость** — S1/S2 разобраны и отклонены, S3 не прошёл гейт.
   Узкое место — входной softirq одного внешнего UDP-потока на одном CPU,
   а не NAPI. Порядок:
   - **Разгрузка softirq** — A/B размещения crypto-воркеров и iperf3,
     RPS/XPS на veth; цель — снять `sys` с CPU приёма.
   - **UDP GRO/батчирование** на сокете модуля — снизить стоимость
     softirq на пакет.
   - **Несколько внешних потоков на пира** — per-device `ExtraPorts`
     уже реализован (0…8, по умолчанию 0); осталось решить, нужен ли
     per-peer набор и как он меняет NAT-модель.
   - **Альтернатива** — принять потолок одного пира и целить в агрегат
     (4 пира уже дают +146…+178%).
2. **Деградация 10 → 50 пиров** (главный регресс): 8.117 → 5.194 Гбит/с
   (−36%), fairness 1.24 → 9.1 при CPU 93–94%. `awg-kernel` в тех же условиях
   держит 7.588 Гбит/с и fairness 1.75. Профилировать per-peer путь
   (`receive.c`, `send.c`, `socket.c`): найти, где теряется параллелизм и
   почему один поток забирает полосу. Матрица —
   [`../docs/BENCHMARKS-2026-11-21.md`](../docs/BENCHMARKS-2026-11-21.md), §6.1.
3. `perf record -g`, `perf stat`, `bpftrace` по `queue_work_on`,
   `process_one_work`, `udp_sendmsg`, `napi_gro_receive` — найти оставшийся
   последовательный участок внутри пира (`receive.c`, `send.c`, `socket.c`).
4. UDP GRO на сокете модуля — только если профилирование подтвердит, что
   приём датаграмм стал узким местом одиночного пира (ожидание 2–4%).
5. CI: сборка против 7.x, netns-тесты, `-Werror`.
6. Проставить тег `kernel-v0.4.1`: `umbrawg-dkms.spec` и `debian` уже
   согласованы на 0.4.1, после тега остаётся `updpkgsums` для стабильного
   AUR-пакета.
7. **FEC RTT** — снизить block timeout (сейчас 5 мс) и сделать ранний
   partial flush: в матрице 2026-11-21 FEC добавляет ≈4–5 мс RTT.
8. **AES-256-GCM и mixed** — снято: на одном пире AES 3.003 против 3.15
   (−4.7%, шум), на пяти 7.620/7.172 (+10.6%/+4.1%), на 2% — 1.627/1.421.
   Осталось: разобрать рост UDP-CPU с AES/mixed (25 → 40%) и оценить
   mixed-fairness/шейпинг; по умолчанию держать ChaCha.
9. **Multi-peer 100** — не тестировались: у Rust прогноз ~4.3 ГБ, у `awg-go`
   50 пиров уже невозможны (>8 ГБ). Возвращаться только при большем стенде.
10. **BBR** — держать `off` по умолчанию и не включать с FEC: на чистом
    канале −17…−24%, на потерях без FEC выигрыша нет.

Не возвращаться к P0-3/P0-4 и TX-коалесингу, threaded NAPI не отключать без
новых замеров.

## Пакетирование и релиз

- `.github/workflows/kernel-packaging.yml` (CI-сборка пакетов, а не кода модуля):
  - `arch` (`archlinux:latest`) — `makepkg -f --noconfirm --nodeps` для
    `contrib/arch/umbrawg-dkms-git`, проверка `/usr/src/umbrawg-<pkgver>`
    (`dkms.conf` с `PACKAGE_VERSION` и `MAKE="make LLVM=1 …"`, `version.h`,
    `uapi/umbrawg.h`, исходники) и сборка модуля из **упакованных** исходников;
  - `rpm` (`fedora:latest`) — тарбол из чекаута, `Version:` в
    `umbrawg-dkms.spec` заменяется на версию из `src/version.h` в форме
    `0.4.1` (дефис в RPM `Version` недопустим), затем `rpmbuild -ba`
    и проверка `rpm -qlp`;
  - `deb` (`debian:trixie`) — `dpkg-buildpackage -b -us -uc`, проверка
    содержимого `.deb`. Нужен пакет `dh-dkms`: в trixie addon `--with dkms`
    вынесен отдельно, без него `dh clean` падает;
  - `релиз` на тег `kernel-v*` — `.pkg.tar.zst`, `.rpm`, `.deb`, `SHA256SUMS`.
- Версия тега = `UMBRAWG_VERSION` из `src/version.h` (`kernel-v0.4.1`).
- Секретов не нужно: AUR и Copr не затрагиваются, публикация ручная.
- `debian/changelog`, `umbrawg-dkms.spec`, `src/version.h`, `src/Makefile`
  и `src/dkms.conf` согласованы на `0.4.1`; `.deb` ставит
  `/usr/src/umbrawg-0.4.1`. Перед первым релизом остаётся проверить
  `debian/rules` на предмет создания второго каталога из legacy-версии и
  обновить `contrib/arch/` (`updpkgsums`).
- RPM собирается с версией из `version.h`, Arch-пакет — по `UMBRAWG_VERSION`;
  `.deb` — по `debian/changelog`. Перед первым релизом версии нужно свести.
- DKMS-пакеты содержат только исходники: для сборки на машине нужны
  заголовки ядра (`linux-headers`, `kernel-devel`) и тулчейн. `LLVM=1`
  обязателен только для ядер, собранных clang; в Arch-контейнере ядро собрано
  GCC, поэтому CI выбирает компилятор по `CONFIG_CC_IS_CLANG`.
- Стабильный `contrib/arch/umbrawg-dkms` в CI не собирается: в `sha256sums`
  заглушка `TODO_UPDPKGSUMS_AFTER_FIRST_TAG`, после тега нужны `updpkgsums`
  и `makepkg --printsrcinfo > .SRCINFO`.
- Осталось: публикация в AUR (ручная), aarch64 (сборка модуля проверена только
  на x86_64 с ядром 7.3.4), прогон workflow в GitHub Actions.
