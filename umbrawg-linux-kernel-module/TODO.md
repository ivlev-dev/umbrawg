## Текущее состояние

- Ветка `master`, всё слито и запушено.
- Переименование AmneziaWG → UmbraWG, `awg` → `uwg`; genl-семейство `umbrawg`, модуль `umbrawg`.
- Удалены `src/compat/` и `src/crypto/` (zinc): 35 742 → 9 077 строк (−74,6%), требуется Linux ≥ 7.0.
- Криптография — только in-kernel API: `chacha20poly1305`, `blake2s`, `curve25519`, `chacha`.
- Netlink/UAPI 3.1: полный набор атрибутов, валидация диапазонов, parity-тесты.
- Оптимизация: per-CPU очереди и батчирование крипто-воркеров в `queueing.c`,
  `device.c`, `send.c`; коалесинг пробуждений крипто-воркеров (коммит

- Профилирование `perf`/`bpftrace` по-прежнему не завершено: изменения приняты по A/B-замерам.

### Коалесинг пробуждений — сделан

`queue_work_on` вызывается только на переходе `pending` `0 → 1`; воркер
снимает флаг и перепроверяет кольцо. Влит в `master` (`f0333de`).

A/B, 5 раундов с чередованием, медианы Мбит/с:

|---|---|---|---|---|---|
| 1c | obf0 | 1 | 2282 | 2416 | +5.85% |
| 1c | obf0 | 10 | 1932 | 2131 | +10.27% |
| 1c | obf1 | 1 | 2274 | 2324 | +2.19% |
| 1c | obf1 | 10 | 1814 | 1742 | −3.96% |
| 3c | obf0 | 1 | 2357 | 2397 | +1.71% |
| 3c | obf0 | 10 | 1993 | 1970 | −1.15% |
| 3c | obf1 | 1 | 2296 | 2399 | +4.49% |
| 3c | obf1 | 10 | 1767 | 1754 | −0.75% |

- UDP 1 Гбит/с: ~0 (потолок линии). UDP без лимита: +1.4…+5.3% по медианам,
  медиана парных Δ +1.0% (11+/9−).
- `perf`: `queue_work_on` 5.86→4.89%, `__queue_work` 5.56→4.55%,
  `try_to_wake_up` 7.29→6.00%.
- Вывод: безопасно, **+2…+4%** на CPU-bound одиночном TCP; агрегатный эффект
  около нуля, принято как попутная оптимизация.

### Масштабирование по пирам — главный результат

`master`, 3c, `conns=10`, UDP без лимита, медианы Мбит/с. 4 пары
«устройство↔пир» со своими сокетами:

| Протокол | Профиль | 1 пир | 2 пира | 4 пира |
|---|---|---|---|---|
| TCP | obf0 | 1790 | 3440 (+92%) | 4778 (+167%) |
| TCP | obf1 | 1674 | 3126 (+87%) | 4122 (+146%) |
| UDP | obf0 | 2317 | 3079 (+33%) | 3662 (+58%) |
| UDP | obf1 | 2125 | 2439 (+15%) | 2974 (+40%) |

Один сокет на сервере (4 пира на одном устройстве): TCP obf0 1830 → 4875
(+166%), obf1 1580 → 4394 (+178%). При 4 пирах CPU0–2 73–87%, CPU3–5 94–100%,
top thread `napi/uwgq0-0` 45–56%; UDP-плато ~3.6 Гбит/с (obf0; obf1 ~3.0),
ограничение — softirq/приложение.

- Одиночный пир упирается в свой NAPI: **~2.2–2.4 Гбит/с** TCP.
- Ёмкость растёт шардированием по пирам, а не числом соединений или RPS:
  один сокет и четыре сокета дают одинаковый прирост.
- Путь к целевым +60% на 3c — число пиров, а не разгон одиночного потока;
  следующий шаг — per-peer ёмкость.

Подробности: [docs/PERFORMANCE.md](docs/PERFORMANCE.md).

### Почему 3 соединения не растут

Один пир = один внешний UDP-сокет + один threaded NAPI-поток + одна in-order
очередь. Параллелится только крипта (per-CPU воркеры), приём из сокета и TX
идут последовательно на пира. RPS/XPS на veth в замерах выключены. Замеры
1/2/4 пиров подтверждают: узкое место — per-peer NAPI, а не сокет.

### Отклонено, не мержить

- **P0-3** (`get_cpu` вместо round-robin выбора CPU): −12…−26% TCP, UDP-потери
  до 10%, ретрансмиты ×1.6. Причина — крипта перестаёт размазываться по CPU.
- **P0-4** (inline-обработка при пустой очереди, ветка `feature/perf-final`):
  те же −12…−26% TCP, потери до 10%, ретрансмиты ×1.6. Причина — RX попадает
  внутрь TX-воркера.
- **TX-коалесинг** (второй `pending`/`queue_work_on` на TX-очередь пира,
  `feature/wakeup-batch-tx`): UDP без лимита −4…−6%, 17/20 парных прогонов
  отрицательные.
- **Отключение threaded NAPI**: −11…−13% TCP.
- **Ветка `wire-correct`** (по одной датаграмме на пакет): −36…−41%.

### В работе

- **Per-peer ёмкость** — главное направление: S2 (диспетчер + пул доставки
  уровня устройства, `K <= nCPU`). Порядок работ: P0 perf-гейт, P1 RPS на
  `uwg0` и дешёвые рычаги, P2 прототип `K=1/2/4`; дизайн —
  [docs/PEER-SHARDING.md](docs/PEER-SHARDING.md).
- **UDP GRO на сокете модуля**: выгода 2–4% для одиночного пира остаётся
  гипотезой.
- Полная матрица (1/2/4/5 пиров × соединения × потери × MTU × обфускация).

## Сборка и проверка

```sh
cd src
make LLVM=1            # обязательно для ядер, собранных clang (Arch/CachyOS)
sudo insmod umbrawg.ko
sudo ip link add dev uwg0 type umbrawg
sudo ip link del uwg0
sudo rmmod umbrawg
```

`srcversion` не годится для проверки пересборки: при правках только в
заголовках он не меняется. Смотрите время `.ko` или лог сборки.

Debug-сборка с селфтестами (allowedips, counter, ratelimiter):

```sh
make module-debug LLVM=1
```

Проверка netlink-паритета 3.1:

```sh
src/tests/netlink-parity.sh
```

## Что работает

- Noise IK, cookie, rekey/keepalive/reject-таймеры.
- Обфускация 3.1: `H1..H4`, `S1..S4`, `Jc/Jmin/Jmax`, `I1..I5`, header protection,
  `ContentPaddingAddition`, `RandomTrailers`, `DisableCookies`.
- GSO на отправке (стандартный UDP GSO, jumbo до 23 КБ) и GRO на приёме TUN,
  per-CPU крипто-очереди.
- Interop GSO-агрегации с `go`, `rust` и `amneziawg` проверен в обе стороны,
  фрагментов на проводе 0.
- Совместимость с userspace-демоном `umbrawg` (Rust) в обе стороны, с обфускацией и без.

## Известные проблемы

- Версии упаковки согласованы на `3.1.20261113-02` (`3.1.20261113_02` в RPM
  `Version`): `src/version.h`, `debian/changelog`, `umbrawg-dkms.spec` и
  Arch-пакеты. `src/Makefile` (`UMBRAWG_VERSION`) и `src/dkms.conf` по
  умолчанию содержат `1.0.0` и переопределяются при сборке пакетов. Осталось
  проставить тег `v3.1.20261113-02`.
- Если инициирует ядро, первая попытка handshake теряется, когда userspace-демон
  ещё не забиндил UDP-порт; соединение поднимается на ретрае через 5 с. Порядок
  настройки: сначала userspace, затем ядро.
- `make` без `LLVM=1` на clang-ядрах падает на флагах (`-fms-anonymous-structs` и др.).
- Поддержка 6.x и старее сознательно удалена.
- UDP GRO на сокете модуля отсутствует (`gro_receive = NULL`, `ACCEPT_L4` не
  выставлен); оценка выгоды 2–4% для одиночного пира — гипотеза, не измерено.
- Полная матрица замеров (1/2/4/5 пиров, соединения, потери) ещё не прогнана:
  масштабирование проверено только на 1, 2 и 4 пирах.
- UDP-потери в замерах — переполнение приёмного буфера `iperf3`
  (`RcvbufErrors`), а не дропы туннеля; в diag стенда есть `QUEUES`/`RPS` и
  счётчики фрагментации.

## Что делать дальше (по приоритету)

1. **Per-peer ёмкость (S2)** — главное направление. Шардирование по пирам —
   путь к ёмкости устройства; следующий шаг — ёмкость каждого пира по потокам.
   Порядок:
   - **P0** — perf-гейт под `3c c10`: измерить `X` (диспетчер) и `Y`
     (GRO/стек); гейт `Y ≥ 0.5 · X`, иначе S2 не реализовывать.
   - **P1** — RPS на `uwg0` (`rps_cpus`, `netdev_max_backlog`) и A/B дешёвых
     рычагов: NAPI weight 64→128/256, `gro_normal_batch` 8→32. Если цель
     достигнута без кода — S2 не нужен.
   - **P2** — прототип: только TCP, `module_param rx_shards`, пул доставки
     уровня устройства, `K=1/2/4`; затем измерения.
   Цель: `3c c10` ≥ ~3090/2810 Мбит/с (+50% к 2056.4/1875.3 в том же
   прогоне). `3c c1` и `1c` — контроли «0%». Дизайн и критерии —
   [docs/PEER-SHARDING.md](docs/PEER-SHARDING.md); per-peer NAPI уже
   реализован (`src/peer.c:57-59`).
2. Полная матрица: 1/2/4/5 пиров × {1, 10, 100, 500} соединений × потери
   {0, 2, 5, 10}% × {TCP 1420, UDP 1340} × {обфускация вкл/выкл}. Стенд — в
   `umbrawg-tools/bench`.
3. `perf record -g`, `perf stat`, `bpftrace` по `queue_work_on`,
   `process_one_work`, `udp_sendmsg`, `napi_gro_receive` — найти оставшийся
   последовательный участок внутри пира (`receive.c`, `send.c`, `socket.c`).
4. UDP GRO на сокете модуля — только если профилирование подтвердит, что
   приём датаграмм стал узким местом одиночного пира (ожидание 2–4%).
5. CI: сборка против 7.x, netns-тесты, `-Werror`.
6. Проставить тег `v3.1.20261113-02`: версии `umbrawg-dkms.spec` и `debian`
   уже согласованы, после тега остаётся `updpkgsums` для стабильного AUR-пакета.

Не возвращаться к P0-3/P0-4 и TX-коалесингу, threaded NAPI не отключать без
новых замеров.

## Пакетирование и релиз

- `.github/workflows/packaging.yml` (CI-сборка пакетов, а не кода модуля):
  - `arch` (`archlinux:latest`) — `makepkg -f --noconfirm --nodeps` для
    `contrib/arch/umbrawg-dkms-git`, проверка `/usr/src/umbrawg-<pkgver>`
    (`dkms.conf` с `PACKAGE_VERSION` и `MAKE="make LLVM=1 …"`, `version.h`,
    `uapi/umbrawg.h`, исходники) и сборка модуля из **упакованных** исходников;
  - `rpm` (`fedora:latest`) — тарбол из чекаута, `Version:` в
    `umbrawg-dkms.spec` заменяется на версию из `src/version.h` в форме
    `3.1.20261113_02` (дефис в RPM `Version` недопустим), затем `rpmbuild -ba`
    и проверка `rpm -qlp`;
  - `deb` (`debian:trixie`) — `dpkg-buildpackage -b -us -uc`, проверка
    содержимого `.deb`. Нужен пакет `dh-dkms`: в trixie addon `--with dkms`
    вынесен отдельно, без него `dh clean` падает;
  - `релиз` на тег `v*` — `.pkg.tar.zst`, `.rpm`, `.deb`, `SHA256SUMS`.
- Версия тега = `UMBRAWG_VERSION` из `src/version.h` (`v3.1.20261113-02`).
  Тегов пока нет.
- Секретов не нужно: AUR и Copr не затрагиваются, публикация ручная.
- **`debian/changelog` содержит legacy-версию `1.0.0`**, поэтому `.deb`
  называется `umbrawg-dkms_1.0.0_all.deb` и ставит `/usr/src/umbrawg-1.0.0`;
  job `deb` выводит предупреждение. Перед реальным релизом changelog нужно
  поднять. Проверено вручную: при версии `3.1.20261113-02` в changelog
  `dh_dkms` и `override_dh_auto_install` создают в пакете оба каталога
  (`umbrawg-1.0.0` и `umbrawg-3.1.20261113`), то есть одной правки changelog
  недостаточно — надо чинить `debian/rules`.
- RPM собирается с версией из `version.h`, Arch-пакет — по `UMBRAWG_VERSION`;
  `.deb` — по `debian/changelog`. Перед первым релизом версии нужно свести.
- DKMS-пакеты содержат только исходники: для сборки на машине нужны
  заголовки ядра (`linux-headers`, `kernel-devel`) и тулчейн. `LLVM=1`
  обязателен только для ядер, собранных clang; в Arch-контейнере ядро собрано
  GCC, поэтому CI выбирает компилятор по `CONFIG_CC_IS_CLANG`.
- Стабильный `contrib/arch/umbrawg-dkms` в CI не собирается: в `sha256sums`
  заглушка `TODO_UPDPKGSUMS_AFTER_FIRST_TAG`, после тега нужны `updpkgsums`
  и `makepkg --printsrcinfo > .SRCINFO`.
- Осталось: публикация в AUR (ручная), aarch64 (сборка модуля проверена только
  на x86_64 с ядром 7.3.4), прогон workflow в GitHub Actions.
